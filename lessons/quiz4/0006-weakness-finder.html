1 · File system calls: open, read, write, lseek, close

30-second refresher open(path, flags, mode) returns a small integer, the file descriptor (fd), or −1 on error. Every open file has a current offset. read(fd, buf, n) reads up to n bytes from the offset, moves the offset forward, and returns how many it read: 0 means end of file, −1 means error. lseek(fd, x, whence) moves the offset to x (SEEK_SET), current + x (SEEK_CUR) or size + x (SEEK_END), and returns the new offset. Lesson 2

1.1 · A file is 60 bytes long. A program opens it and calls read(fd, buf, 100). What does read return?

It can only read what's there: 60. Asking for more than is left is allowed; you just get a "short read".

1.2 · Right after that, it calls read(fd, buf, 100) again. Return value?

The offset is at 60, the end. read returns 0 at end-of-file. That's how loops like while ((n = read(…)) > 0) know when to stop.

1.3 · open("missing.txt", O_RDONLY) is called on a file that doesn't exist. What does it return?

  1. 0
  2. NULL
  3. −1
  4. The next free fd

System calls signal failure with −1 and set errno. NULL is what fopen (the C library version) returns. 0 is a valid fd: standard input.

1.4 · A file is 1,500 bytes. What does lseek(fd, 0, SEEK_END) return?

SEEK_END means file size + 0 = 1500. This is a common way to find a file's size.

1.5 · A 5,000-byte file. lseek(fd, 1000, SEEK_SET); read(fd, buf, 200); x = lseek(fd, -50, SEEK_CUR); What is x?

1000, then the read moves the offset to 1200, then back 50: 1150.

1.6 · Which flag makes every write go to the end of the file, even after an lseek?

  1. O_TRUNC
  2. O_APPEND
  3. O_CREAT
  4. O_RDWR

O_APPEND. O_TRUNC empties the file when it's opened, O_CREAT creates it if it's missing, and O_RDWR allows both reading and writing.

1.7 · open("new.txt", O_WRONLY), and new.txt doesn't exist yet. What happens?

  1. An empty file is created
  2. It opens /dev/null instead
  3. It waits for the file to appear
  4. It fails and returns −1

Without O_CREAT, open never creates a file. To create one you need O_WRONLY | O_CREAT plus a mode such as 0644.

1.8 · What's the main difference between fopen and open?

  1. fopen adds a user-space buffer and returns a FILE *
  2. fopen skips the kernel and reads the disk directly
  3. open only works on directories
  4. open returns a FILE * and fopen returns an int

fopen is a C library wrapper: it calls open underneath and adds a buffer, so many small fgetc calls become a few big read system calls. Everything still goes through the kernel.

1.9 · A program reads a 4,500-byte file with a loop of read(fd, buf, 1024) until read returns 0. How many times is read called in total?

1024, 1024, 1024, 1024 (4,096 so far), then 404, then 0: 6 calls. If you typed 5, you forgot the last call, the one that returns 0 and ends the loop.

2 · File descriptor tables, fork, dup, redirection

30-second refresher Three tables. fd table: one per process, maps fd number → an open-file entry. Open-file table: one for the whole system; each entry holds the offset, the access mode and a reference count. v-node table: one entry per actual file. Each open() makes a new open-file entry. fork() and dup() copy fds that point at the same entry, so they share an offset. dup2(old, new) makes new point where old points. Lesson 2

2.1 · A fresh program, with only stdin, stdout and stderr open, calls open() once. Which fd does it get?

0, 1 and 2 are taken, and open returns the lowest free number: 3.

2.2 · Where is a file's current offset stored?

  1. In the per-process fd table
  2. In the open-file table entry
  3. In the v-node table entry
  4. In the file's inode on disk

In the open-file entry. That's why two fds sharing one entry (after fork or dup) share an offset, and two separate open() calls don't.

2.3 · Two unrelated processes each call open() on the same file. How many open-file-table entries now refer to that file?

One per open() call: 2. Each has its own offset.

2.4 · Same situation. How many v-node table entries refer to it?

It's one file, so 1. Both open-file entries point to it, which is why one process's writes are visible to the other.

2.5 · The file holds PQRSTUVW. A process opens it, reads 3 bytes, then forks. The parent reads 2 bytes, and then the child reads 1 byte. Which byte does the child read?

  1. P
  2. S
  3. T
  4. U

One shared offset. After PQR it's 3. The parent reads ST, moving it to 5. The child gets U.

2.6 · Same file, but this time the parent and child each call open() after the fork. The parent reads 3 bytes, then the child reads 1. The child gets…

  1. S
  2. Q
  3. P
  4. T

Separate open() calls mean separate offsets. The child's is still 0: P.

2.7 · After a fork, the parent calls close(fd). Can the child still read through its copy of fd?

  1. Yes; the entry's count drops from 2 to 1
  2. No; close removes the entry for both
  3. Only if the child reopens the file
  4. Only if the parent exits first

close only removes this process's fd and decrements the reference count. The entry is freed when the count reaches 0.

2.8 · Starting with 0–2 open: a = open(…); b = open(…); close(a); c = open(…); d = dup(b); What is d?

a = 3, b = 4. Closing 3 frees it, so c = 3. dup also takes the lowest free number: 5.

2.9 · A process opens a file once, forks, and then the child calls dup() on that fd. What is the open-file entry's reference count?

open 1, fork 2, dup 3. All three fds share one offset.

2.10 · After fd = open("out.txt", O_WRONLY|O_CREAT|O_TRUNC, 0644); dup2(fd, 1);, where does printf("hi") go?

  1. The terminal
  2. Nowhere; stdout is closed
  3. Into out.txt
  4. Both the terminal and out.txt

printf writes to fd 1, and dup2 made fd 1 point at out.txt's entry. This is exactly how the shell runs cmd > out.txt.

2.11 · Which pair implements sort < data.txt (read standard input from a file)?

  1. fd = open("data.txt", O_WRONLY); dup2(fd, 1);
  2. fd = open("data.txt", O_RDONLY); dup2(fd, 0);
  3. fd = open("data.txt", O_RDONLY); dup2(0, fd);
  4. fd = open("data.txt", O_RDONLY); dup(0);

Input means fd 0, opened for reading, and dup2(the fd you have, the fd you want to replace). Option 3 is backwards: it would make fd point at the terminal.

2.12 · fd = open(…) returns 3. Then dup2(3, 0); close(3); Which fds now refer to the file?

  1. Only fd 0
  2. Only fd 3
  3. Both fd 0 and fd 3
  4. Neither of them

dup2 gives fd 0 its own reference (count 2). close(3) drops one (count 1). The file stays open through fd 0, which is the clean way to finish a redirection.

3 · Disks and file layout performance

30-second refresher access time = seek + rotational latency + transfer. One rotation = 60,000 / RPM ms. Average rotational latency = half a rotation. Transfer of one sector = rotation ÷ sectors per track. Reading blocks that sit next to each other pays the seek and rotation once; scattered blocks pay them every time. Lesson 1

3.1 · How long is one full rotation at 15,000 RPM, in ms?

60,000 / 15,000 = 4 ms.

3.2 · Seek 9 ms, 7200 RPM, 400 sectors per track. Average time to read one sector, in ms? (2 decimals)

Rotation 8.3333. Half = 4.1667. Transfer = 8.3333 / 400 = 0.0208. 9 + 4.1667 + 0.0208 = 13.1875 ≈ 13.19.

3.3 · Same disk. A 100-sector file sits in consecutive sectors on one track. Time to read the whole file? (2 decimals)

Seek and wait once, then 100 sectors stream by: 9 + 4.1667 + 100 × 0.0208 = 15.25.

3.4 · Same disk and file, but every sector is somewhere random. Time to read it all? (2 decimals)

Each sector costs the full 13.1875: 100 × 13.1875 = 1318.75 ms, which is about 86 times slower. That gap is the whole reason file layout matters.

3.5 · For one random sector read on a typical hard disk, which part usually takes the longest?

  1. Seek
  2. Transfer
  3. The CPU copying data
  4. Writing the inode

Seeks are several milliseconds. Transfer of one sector is a tiny fraction of a millisecond (0.02 ms in 3.2).

3.6 · The disk now spins twice as fast. Which get smaller? Pick all that apply.

  1. Average seek time
  2. Average rotational latency
  3. Transfer time per sector
  4. Number of sectors per track

Rotation and transfer both depend on how fast it spins. Seek is the arm, and sectors per track is how the platter is formatted.

3.7 · Why does the OS read and write disks in whole blocks rather than single bytes?

  1. Bytes on a disk have no addresses
  2. Blocks are encrypted, bytes are not
  3. The CPU can't load single bytes
  4. Getting there costs far more than reading

Once you've paid milliseconds for seek and rotation, reading a few more bytes is nearly free. The hardware also only reads whole sectors.

4 · Fixed-size blocks and file indexes

30-second refresher A file is stored in fixed-size blocks. Byte offset x is in logical block LBN = ⌊x / B⌋. The file's index maps LBN → PBN (where the block physically is). Flat: one big array. Extents: (start, length) runs. Hybrid (Unix inode): d direct pointers, then single, double and triple indirect. p = B ÷ address size; first single offset = d·B; max size = (d + p + p² + p³)·B. Reads with the inode cached: direct 1, single 2, double 3, triple 4. Lesson 3

4.1 · What's the main advantage of fixed-size blocks over storing each file as one variable-length chunk?

  1. Files never waste any space at all
  2. Every file can be read with one seek
  3. Any free block can be used: no external fragmentation
  4. Indexes are no longer needed

With variable chunks, free space breaks into gaps too small to use (external fragmentation), and files can't grow in place. With fixed blocks, any free block fits anywhere.

4.2 · Blocks are 4096 bytes. A 5,000-byte file wastes how many bytes in its last block?

It needs 2 blocks = 8,192 bytes. 8,192 − 5,000 = 3,192. That waste is internal fragmentation, the price of fixed-size blocks.

4.3 · Blocks are 1024 bytes. Which LBN holds byte offset 9,000?

9,000 / 1024 = 8.79, so 8.

4.4 · And at what position inside that block is byte 9,000?

9,000 − 8 × 1024 = 808 (equivalently, 9,000 mod 1024).

4.5 · A flat index has room for 1,000 block numbers, and blocks are 4 KB (4096 bytes). Largest file in bytes?

1,000 × 4096 = 4,096,000.

4.6 · Extents (start, length): (40, 5) (300, 2) (77, 10). Which PBN holds LBN 6?

6 − 5 = 1, so it's 1 into the second extent: 301.

4.7 · Same extents. Which PBN holds LBN 15?

15 − 5 = 10, then 10 − 2 = 8, so 8 into the third extent: 77 + 8 = 85.

4.8 · 4096-byte blocks, 4-byte addresses, 12 direct pointers. Smallest byte offset that needs the single indirect block?

12 × 4096 = 49,152.

4.9 · Same inode. Smallest offset that needs the double indirect block?

p = 4096 / 4 = 1024. (12 + 1024) × 4096 = 4,243,456.

4.10 · 512-byte blocks, 4-byte addresses, 10 direct, 1 single, 1 double, 1 triple. Largest file in bytes?

p = 128. Blocks = 10 + 128 + 16,384 + 2,097,152 = 2,113,674. × 512 = 1,082,201,088.

4.11 · With the inode already in memory, how many disk reads to get a byte under the triple indirect pointer?

Triple block → double block → single block → data block: 4.

4.12 · Inode with 12 direct pointers. A file is 13 blocks long. Counting data blocks and index blocks, but not the inode itself, how many disk blocks does it use?

13 data blocks plus 1 single indirect block to point at the 13th: 14.

4.13 · Why does the Unix inode have direct pointers at all, instead of only indirect ones?

  1. Direct pointers allow bigger files
  2. Most files are small, and direct pointers make them 1 read
  3. Indirect blocks can't be cached
  4. Directories need direct pointers

Most files are small. Direct pointers make them fast and cheap, and the indirect levels are only used by the few big files.

4.14 · File system A has smaller blocks than B. Which are true of A? Pick all that apply.

  1. It wastes less space on tiny files
  2. It reads a big file with fewer disk accesses
  3. It has higher throughput on big files
  4. It reads one individual block faster

Smaller blocks: less internal fragmentation and a quicker single-block transfer, but more blocks per file, so more accesses and lower throughput.

5 · Directories, paths and metadata

30-second refresher A directory is a file of (name, inode number) entries. The inode holds everything about a file except its name: size, owner, permissions, times, link count and the block map. stat() returns the inode's information. To resolve /a/b/c you read each directory's inode and data block in turn. With nothing cached, one-block directories and k names: 2(k + 1) reads to reach the file's first byte. Lesson 4

5.1 · Read the first byte of /a/b/c.txt. Nothing cached, inodes in separate blocks, each directory one block. Disk reads?

k = 3. /, a and b each cost inode + data (6), then c.txt's inode + first block (2). 8.

5.2 · Same, but the root directory's inode and its data block are already cached. Reads?

8 − 2 = 6. Real systems almost always cache the root, so this variant is common.

5.3 · Nothing cached, but directory b is big and spans 2 blocks, with c.txt's entry in the second one. Fewest reads to read c.txt's first byte?

/ (2), a (2), b's inode plus both of b's blocks (3), then c.txt's inode and first block (2): 9. The name could be in either block, and here it's in the second, so you read both.

5.4 · Which of these does stat() not tell you?

  1. The file's size in bytes
  2. The file's link count
  3. The file's name
  4. The file's inode number

stat reports the inode's contents, and the name isn't in the inode. You already know the name: you passed the path in.

5.5 · Where are a file's permission bits stored?

  1. In its directory entry
  2. In the open-file table
  3. In the first data block
  4. In its inode

In the inode, with the other metadata. That's why all hard links to a file share the same permissions.

5.6 · A directory d contains 3 subdirectories and 4 regular files. What is d's link count?

d's entry in its parent (1) + its own . (1) + each subdirectory's .. (3) = 5. Regular files don't add anything to d's count. A new, empty directory therefore has link count 2.

5.7 · mv /home/u/a.txt /home/u/docs/a.txt on the same file system. What does it do on disk?

  1. Adds an entry in docs and removes the old one; no data copied
  2. Copies every data block to a new place
  3. Creates a new inode and copies the old one
  4. Changes the inode's block pointers

The inode and data stay where they are. Only the directory entries (name → inode) change, which is why moving even a huge file is instant on the same file system.

5.8 · s is a symbolic link to big.dat. What's the difference between stat("s") and lstat("s")?

  1. They are always the same
  2. stat follows the link to big.dat; lstat describes the link itself
  3. lstat follows the link; stat describes the link itself
  4. lstat only works on directories

"l" for link: lstat doesn't follow it. That's how ls -l can show s -> big.dat.

6 · Hard and symbolic links

30-second refresher Hard link (ln a b): a second directory entry with the same inode number. Link count goes up by 1. It can't cross file systems or point to a directory. Symbolic link (ln -s a b): a new small file whose contents are the path. It can cross file systems, point to directories, and dangle if the target disappears. Data is freed only when the link count hits 0 (and nobody has it open). Lesson 4 §3

6.1 · touch a; ln a b; ln -s a c. Link count of a's inode?

a and b are two names for the same inode: 2. The symlink c is a different file and doesn't count.

6.2 · Then rm a. Which still works?

  1. cat c only
  2. cat b only
  3. Both of them
  4. Neither of them

b is the same inode, now with count 1. c holds the text "a", which no longer resolves, so it dangles.

6.3 · Which command fails? (/mnt/usb is a different file system.)

  1. ln -s /mnt/usb/notes n
  2. ln report.txt r2.txt
  3. ln /mnt/usb/notes n
  4. ln -s .. up

A hard link stores an inode number, and inode numbers only mean something on their own file system.

6.4 · Why can't you hard-link a directory?

  1. It could create loops in the directory tree
  2. Directories have no inodes
  3. Directories are too large
  4. Directories are read-only

A hard link from deep inside a directory back to its ancestor would make a cycle, and tools that walk the tree would never finish. Symlinks are fine because tools can choose not to follow them.

6.5 · ln -s /home/u/notes.txt n. How many bytes of data does the symlink n hold?

Its contents are the path text: /home/u/notes.txt = 5 + 2 + 10 = 17 characters. (It doesn't store a terminating zero.)

6.6 · ln a b. What does ls -i a b show?

  1. Different inode numbers, same size
  2. Different inode numbers, b is size 1
  3. The same inode number with link count 1
  4. The same inode number for both

They're the same inode, now with link count 2. Neither name is the "original".

6.7 · ln x y; ln y z; rm x. What is the link count now?

x, y and z all name the same inode (count 3). ln y z links to the inode, not to y. rm x leaves y and z: 2.

7 · Case studies: v6 and ext2

30-second refresher (from general sources, not your slides) Unix v6: 512-byte blocks, 2-byte block numbers, inodes with 8 address slots. A small file uses them as 8 direct pointers. A "large" file uses the first 7 as single indirect and the 8th as double indirect. Directory entries are 16 bytes: a 2-byte inode number and a 14-byte name. Free blocks are kept in a free list. ext2: the disk is split into block groups, each with its own bitmaps and inode table, so a file's inode and data stay close. Inodes have 12 direct + single + double + triple, 4-byte block numbers. Directory entries are variable length, with names up to 255 characters. Lions' Commentary on Unix 6th ed.; ext2 docs; OSTEP ch. 41

7.1 · v6 directory entries are 16 bytes. How many fit in one 512-byte block?

512 / 16 = 32.

7.2 · A v6 entry is a 2-byte inode number plus the name. What's the longest name allowed?

16 − 2 = 14 characters.

7.3 · A v6 small file uses its 8 address slots as direct pointers to 512-byte blocks. Largest small file, in bytes?

8 × 512 = 4,096. Bigger than that, and it becomes a "large" file.

7.4 · A v6 large file: 7 single indirect pointers and 1 double indirect, 512-byte blocks, 2-byte block numbers. Largest file in bytes (from the pointers alone)?

p = 512 / 2 = 256. Blocks = 7 × 256 + 256² = 1,792 + 65,536 = 67,328. × 512 = 34,471,936. Note there are no direct pointers in this mode, and 7 singles rather than 1. Read the setup carefully.

7.5 · ext2 with 2048-byte blocks, 4-byte addresses and 12 direct pointers. Smallest offset that needs the double indirect block?

p = 512. (12 + 512) × 2048 = 1,073,152.

7.6 · How does ext2 keep track of which blocks are free?

  1. A linked free list starting in the superblock
  2. A bitmap in each block group
  3. A flag in every data block
  4. By scanning every inode at boot

One bit per block in a bitmap. v6 used a free list, which scatters a file's blocks over time; bitmaps make it easy to find free blocks near each other.

7.7 · What's the main reason ext2 splits the disk into block groups?

  1. To allow bigger files
  2. To make inode numbers shorter
  3. To keep an inode near its data, cutting long seeks
  4. To allow names longer than 14 characters

It's about performance (Section 3): related things sit close together, so seeks are short.

7.8 · In ext2 a directory entry stores its own length (rec_len). What does that make possible?

  1. Variable-length names, and skipping past deleted entries
  2. Hard links to directories
  3. Files bigger than the disk
  4. Faster reads of file data

Entries aren't a fixed 16 bytes, so each one says where the next starts. Deleting an entry can just grow the previous one's rec_len over it.

7.9 · In a v6 directory, an entry whose inode number is 0 means…

  1. It's the root directory
  2. It's a symbolic link
  3. It's the .. entry
  4. The slot is unused (deleted)

Inode 0 isn't a real inode in v6, so it marks an empty slot. The old name bytes may still be visible in a dump. (The v6 root is inode 1; in ext2 it's inode 2.)

9 · Coherence review: MSI and MESI

30-second refresher M = only I have it, and it's dirty. E = only I have it, clean (MESI only). S = clean, others may have it too. I = not valid. For the same line, M and E pair only with I. Two differences: a read miss nobody else has gives S in MSI but E in MESI; and on the course MSI diagram, a remote read of an M line takes it to I, while MESI takes it to S. Quiz 3 Lesson 7

9.1 · MESI. A line is in E, and this core writes to it. New state, and is a bus message needed?

  1. M, and it sends an invalidate
  2. M, silently with no message
  3. S, silently with no message
  4. E, and it writes back

E already means no one else has it, so nothing needs invalidating. This silent upgrade is MESI's whole advantage.

9.2 · MESI. Cores 1 and 2 both hold a line in S. Core 1 writes. What is Core 2's state now?

  1. S
  2. E
  3. M
  4. I

Core 1 must invalidate the other copies before writing; it goes to M and Core 2 goes to I.

9.3 · MSI. Core 1 read-misses on a line nobody else has. Core 1's new state?

  1. S
  2. E
  3. M
  4. I

MSI has no E, so a clean copy is always S.

9.4 · MESI. Core 1 has a line in M, and Core 2 reads it. What happens to Core 1?

  1. It stays in M
  2. It goes to I with no write-back
  3. It writes back and goes to S
  4. It goes to E

The dirty data must reach memory (or Core 2), and now there are two copies, so S. On the course MSI diagram it would go to I instead.

9.5 · Two caches, the same set (slot), not necessarily the same address. Can both be in M?

  1. Yes, they can hold different lines
  2. No, M is exclusive
  3. Only in MSI
  4. Only if both are clean

Same slot doesn't mean same memory line. "Exclusive" is per memory line, so any pair is possible here.

9.6 · Same memory line, two MESI caches. Which pair is impossible?

  1. I and M
  2. E and S
  3. S and S
  4. I and I

E means nobody else has a copy, so it can't coexist with S.
