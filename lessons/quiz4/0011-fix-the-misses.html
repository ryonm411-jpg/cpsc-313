1 · Return values: what read and open actually give back (missed 1.1, 1.3, 1.8, 1.9)

Rule read(fd, buf, n) returns the number of bytes it actually got. That's n, or fewer if the file runs out first (a short read). At end of file it returns 0. Any failing system call, open included, returns −1.
Counting read calls: a loop that stops when read returns 0 makes ⌈size ÷ n⌉ calls that return data, plus one more that returns 0. That's true even when n divides the size exactly.
fopen is a C library wrapper around open. It adds a user-space buffer and gives you a FILE * instead of an int.

A 700-byte file. read(fd, buf, 512) returns 512. What does the next read(fd, buf, 512) return?

Only 700 − 512 = 188 bytes are left, so it returns 188, a short read. The call after that returns 0.

A 3,072-byte file is read with read(fd, buf, 1024) in a loop until read returns 0. How many read calls is that in total?

3 calls return 1024 bytes each, and the 4th returns 0. Even when n divides the size exactly, the loop needs that extra call to find out the file has ended.

The same loop with read(fd, buf, 512) on a 2,000-byte file. Total calls?

⌈2000 ÷ 512⌉ = 4 calls return data (512, 512, 512, 464), plus 1 that returns 0, for 5.

open("/root/secret", O_RDONLY) fails because you don't have permission. What's in the returned value?

  1. 0
  2. −1
  3. 3
  4. NULL

Every Unix system call reports failure by returning −1 and setting errno. NULL is what fopen returns, because it returns a pointer.

2 · fd numbers, dup and dup2 (missed 2.1, 2.6, 2.8–2.12)

Rule A new fd always takes the lowest free number. 0, 1 and 2 are already open, so the first open gets 3. If you close 3, the next open or dup reuses 3.
dup2(old, new) makes fd new point where old points. To remember the order, read it as "copy old into new". Redirecting output is dup2(fd, 1). Redirecting input is dup2(fd, 0). Shells then call close(fd), which leaves only 0 or 1 pointing at the file.
Reference count = the number of fds, in all processes, that point at the open-file entry.
Does the offset get shared? fds made by dup, dup2 or fork share one entry, so they share one offset. Every open() call makes a new entry, so it gets its own offset that starts at 0.

0–2 are open. a = open(…); b = open(…); c = dup(a); close(b); d = open(…); What is d?

a = 3, b = 4, c = 5. close(b) frees 4, which is now the lowest free number, so d = 4.

fd = open(…) returns 3. Then dup2(3, 0); close(3); x = open(…); What is x?

After close(3), 3 is the lowest free number again (0, 1 and 2 are in use, and 0 now points at the file). So x = 3.

fd = open("log.txt", O_WRONLY|O_CREAT|O_TRUNC, 0644); dup2(fd, 2); Where does an error message written to stderr go?

  1. The terminal only
  2. Nowhere, it's lost
  3. Into the log.txt
  4. Both of those places

Standard error is fd 2. dup2(fd, 2) points fd 2 at log.txt's entry, so anything written to fd 2 goes into the file.

Which line sends a program's standard output to fd?

  1. dup2(1, fd);
  2. dup2(fd, 0);
  3. dup2(0, fd);
  4. dup2(fd, 1);

"Copy old into new": the file (fd) is copied into slot 1, stdout. dup2(1, fd) does the reverse: it points fd at the terminal.

A process opens a file once and forks. Then the parent calls dup2(fd, 7). What is the open-file entry's reference count?

Three fds point at the entry: the parent's fd, the parent's fd 7, and the child's inherited copy of fd. That makes 3.

The file holds ABCDEFGH. fd1 = open(f); fd2 = open(f); read(fd1, buf, 4); read(fd2, &c, 1). What is c?

  1. A
  2. E
  3. D
  4. B

Two separate open() calls make two entries with two offsets. fd2's offset is still 0, so it reads A.

Same file, but this time fd2 = dup(fd1). read(fd1, buf, 4); read(fd2, &c, 1). What is c?

  1. A
  2. E
  3. D
  4. B

dup shares the entry, so it shares the offset. The offset is already at 4, so fd2 reads E.

3 · Index sizes and where each pointer level starts (missed 4.2, 4.6, 4.8–4.10, 7.3, 7.4)

Rule p = B ÷ address size, the number of pointers that fit in one index block. Each pointer covers a number of blocks: direct covers 1, single indirect p, double p², triple p³.
Max size = (number of each pointer type × the blocks it covers, all added up) × B. If there are 7 single indirect pointers, that term is 7p.
The first offset a level needs is the total size of every level before it: single starts at d·B, and double starts at (d + p)·B. Don't add 1. Offsets start at 0, so d direct blocks cover bytes 0 to d·B − 1.
Wasted space in the last block = ⌈size ÷ B⌉·B − size.
To find a block in a list of extents, subtract each extent's length from the LBN until what's left is smaller than the next length. The answer is that extent's start + what's left.

For this card: B = 1024, addresses are 4 bytes (so p = 256), and the inode has 10 direct, 1 single, 1 double and 1 triple pointer.

What's the smallest offset that needs the single indirect block?

d·B = 10 × 1024 = 10,240. The direct pointers cover bytes 0 to 10,239.

What's the smallest offset that needs the double indirect block?

(10 + 256) × 1024 = 272,384.

What's the largest file this inode can describe, in bytes?

(10 + 256 + 256² + 256³) × 1024 = (10 + 256 + 65,536 + 16,777,216) × 1024 = 16,843,018 × 1024 = 17,247,250,432. Remember to multiply by B at the end.

A different design, like v6 large files: no direct pointers, 6 single indirect and 1 double indirect, B = 1024, 4-byte addresses. What's the largest file in bytes?

p = 256. Blocks = 6 × 256 + 256² = 1,536 + 65,536 = 67,072. Then × 1024 = 68,681,728.

B = 2048. How many bytes are wasted in the last block of a 5,000-byte file?

The file needs ⌈5000 ÷ 2048⌉ = 3 blocks, which is 6,144 bytes. 6,144 − 5,000 = 1,144 bytes wasted.

The extents are (120, 4), (50, 3), (900, 6). Which PBN holds LBN 9?

Subtract the lengths: 9 − 4 = 5, then 5 − 3 = 2. 2 is less than 6, so it's in the third extent: 900 + 2 = 902.

4 · Disk timing, and why block size matters (missed 3.1, 3.2, 3.7, 4.13, 4.14)

Rule One rotation = 60,000 ÷ RPM ms. Reading one sector costs seek + ½ rotation + (rotation ÷ sectors per track).
Moving the disk head and waiting for the sector to come round costs milliseconds. The transfer itself costs a few hundredths of a millisecond. That's why the OS moves whole blocks at a time: once you've paid to get there, reading extra bytes is almost free. It's also why the inode has direct pointers: most files are small, and direct pointers let a small file be read without any extra index-block reads.
Smaller blocks: less space wasted at the end of each file, and each block transfers faster. But a big file then has more blocks, which means more accesses and lower throughput.

How long is one rotation at 10,000 RPM, in ms?

60,000 ÷ 10,000 = 6 ms.

The seek is 5 ms, the disk spins at 10,000 RPM and there are 300 sectors per track. What's the average time to read one sector, in ms (2 decimals)?

5 + 3 (half a rotation) + 6 ÷ 300 (0.02) = 8.02 ms. Nearly all of it is positioning.

File system X uses bigger blocks than Y. Which are true of X? (Pick all that apply.)

  1. Wastes less space on tiny files
  2. Reads a big file in fewer accesses
  3. Transfers one block in less time
  4. Gets more throughput on big files

Bigger blocks mean fewer accesses and higher throughput on big files. But each block takes longer to transfer, and more of the last block is wasted.

5 · Links and metadata (missed 5.6, 5.8, 6.5, 6.6)

Rule A directory's link count = 2 + its number of subdirectories. The 2 are its entry in its parent and its own .. Each subdirectory's .. adds 1. Regular files inside it add nothing.
A symbolic link's data is the path text you gave it, exactly as written. Its size is the length of that text.
A hard link is the same inode, so ls -i shows the same inode number for both names. lstat describes the link itself (the "l" is for link). stat follows the link to the file it points to.

Directory p contains 5 subdirectories and 2 regular files. What is p's link count?

2 + 5 = 7. The files add nothing.

ln -s ../data/x.csv s. How many bytes of data does s hold?

The text "../data/x.csv" is 13 characters, so 13 bytes. It stores the relative path exactly as given, not the absolute one.

s is a symlink to big.dat. Which call reports big.dat's size?

  1. lstat("s")
  2. lstat("x")
  3. stat("s")
  4. stat("l")

stat follows the link to big.dat. lstat would report the link's own size, which is the length of the text "big.dat" (7).

6 · MESI, and ext2's free-space tracking (missed 9.1, 9.2, 9.5, 7.6)

Rule Writing in E: the line moves to M without any bus message. E already guarantees nobody else has a copy. This is the reason MESI exists.
Writing in S: the core must invalidate the other copies first. The writer moves to M and every other copy goes to I.
The "only one M" rule applies to one memory line. Two caches can both be in M in the same set, because they can hold different lines there.
ext2 tracks free blocks with a bitmap in each block group. v6 used a linked free list.

MESI. Core 3 holds a line in E and writes to it. What happens?

  1. Goes to S, no bus message
  2. Goes to M, sends invalidate
  3. Goes to M, no bus message
  4. Stays E, writes to memory

E means nobody else holds the line, so there's no one to invalidate. The core upgrades to M silently.

MESI. Cores 1, 2 and 3 all hold a line in S. Core 2 writes. What are the states of Cores 1 and 3?

  1. S and S
  2. E and E
  3. M and I
  4. I and I

Core 2 invalidates every other copy and moves to M. Cores 1 and 3 both go to I.

Two caches, same set. Can one be in M while the other is also in M?

  1. Yes, the lines can differ
  2. No, only one M is allowed
  3. Only under MSI, not MESI
  4. Only if neither is dirty

Being in the same set doesn't mean holding the same line. Any pair of states is possible.

How does ext2 find free blocks?

  1. A free list in the superblock
  2. A bitmap in each block group
  3. A free flag in each data block
  4. A scan of every inode at boot

One bit per block. Scanning a bitmap makes it easy to find free blocks that sit next to each other.
