Two smaller topics from your practice set: who shares an offset (I22), and why ext2 was designed differently from v6 (P24, I26).

Slides 4.2, slides 5–12: "If two threads are using the same file descriptor, should they be using the same file offset? Yes." Tutorial 8 solution, Q1–3.

Your three, solved

  • I22.1: dup2 → shared. 770 + 903 = 1673.
  • I22.2: shared. The writes leave the offset at 995 + 1 = 996. The 869-byte read moves it to 1865. readbyte comes from offset 1865, past everything written, so: not enough information. It would only be X if a separate fd started at 0 and skipped exactly 995 bytes.
  • I22.3: T1 opens its own fd, so it doesn't touch fd1's entry. T2's dup2(fd, 6) shares fd1's entry and reads 874. fd1's offset is 874.

fd1 = open(f); fd2 = open(f); write(fd1, 'c' × 500); write(fd1, "X", 1); read(fd2, buf, 500); read(fd2, &b, 1). What is b?

  1. c
  2. not enough info
  3. X
  4. a zero byte

Separate opens give separate offsets. fd2 starts at 0, skips bytes 0–499 (the c's), and reads byte 500, which is the X. Same file data, so it sees fd1's writes.

3 · Practice (P24, I26)

These are the pasted questions. For P24.4–P24.6 I've given my best reasoning; mark them against PrairieLearn and tell me if any are wrong.

P24.2 · Why does the v6 superblock go in block 1?

  1. Different disks are free to put it anywhere
  2. The OS needs a known spot to mount it
  3. Earlier blocks are faster to access
  4. It is a special kind of inode block

To mount a file system, the OS has to read its parameters before it knows anything else, so they must be at a fixed, known address. Block 0 is the boot block. Slides 4.3: "To mount a file system OS must be able to read its super block."

P24.3 · A key goal of v6's linked-list free list?

  1. A full disk needs no free-list blocks beyond the superblock
  2. Blocks come back out in a roughly random order
  3. Quickly assembling a list of every free block
  4. Inserting blocks anywhere by editing PBNs

The list is stored inside the free blocks themselves, so it costs nothing extra: when the disk is full there are no free blocks, and so no list blocks either. Random order is a side effect, not a goal. Listing every free block means walking the whole chain, and it works like a stack, not something you insert into at arbitrary points. (A bitmap would be smaller per block, so option (e) is false too.)

P24.4 · A v6 inode's index behaves like… (pick all)

  1. a single extent
  2. a multi-level index
  3. a hybrid index

My reasoning: a small file uses its 8 slots as 8 tree roots of height 0, like the Tutorial 9 multi-level index with 8 roots. A large file mixes levels in one inode (7 single indirect + 1 double indirect), which is what makes an index hybrid. So both multi-level and hybrid. I'm not certain; check it against PrairieLearn.

P24.5 · What does v6's directory entry scheme focus on? (pick all)

  1. Type metadata for each entry
  2. Easily human-readable names
  3. A small maximum entry size
  4. Easy-to-find entry boundaries
  5. Saving space for tiny names

Fixed 16-byte entries: small, and every boundary is a multiple of 16. There's no type field, and a 1-character name still takes 16 bytes.

P24.6 · What can limit the maximum number of files in v6? (pick all)

  1. The disk's size
  2. The inverse of the inode size
  3. The block size
  4. The bits in an inode number
  5. Data blocks per inode
  6. Inode blocks in the superblock

Every file needs an inode. The count of inodes is inode blocks × inodes per block (block size ÷ inode size), the inode blocks have to fit on the disk, and the 16-bit inumber in the dirent caps it at 65,535. How big a single file can get doesn't limit how many files there are.

I26.1 · Which file system can more easily allocate files contiguously?

  1. ext2
  2. V6
  3. can't tell

Bitmaps let you search for a run of free blocks, and block groups keep a file near its inode. v6's free list gives blocks back in near-random order after a while.

I26.2 · Same address size and block size (≥ 512). Which can represent a larger file?

  1. ext2
  2. V6
  3. can't tell

v6 large: 7p + p² blocks. ext2: 12 + p + p² + p³. The triple indirect wins easily.

I26.3 · Inode in memory, 4-byte addresses, 512-byte blocks. IOs for v6 to read logical block 2 of a 4-block file?

4 blocks ≤ 8, so it's a small file with direct pointers: read just the data block. 1.

I26.4 · Lots of names 9–14 bytes long. Which uses more directory space?

  1. V6
  2. ext2
  3. V6 can't store them
  4. ext2 can't store them
  5. both the same

v6: always 16 bytes (14-character names just fit). ext2: 8-byte header + 9–14 name bytes, 4-byte aligned, which is 20–24 bytes. So ext2 uses more.

ext2 has 8192-byte blocks and 128-byte inodes, with one bitmap block for inodes. How much data can one block group hold? (Slides 4.6)

  1. 64 MB
  2. 8 MB
  3. 1 GB
  4. 512 MB

One bitmap block = 8192 × 8 = 64K bits → 64K blocks × 8 KB = 512 MB. The inode bitmap allows 64K inodes, which at 64 per block take 1024 blocks.
