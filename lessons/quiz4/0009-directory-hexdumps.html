Reading Directory Hexdumps

"Read binary dumps of directories" is a Quiz 4 learning goal, and I25 shows exactly how it's asked. It comes down to one 8-byte header, read over and over.

Your win for today: answer all four I25 question types: name from inode, type from inode, inode from name, and number of valid entries. You'll do it without a hex converter, since there's no internet in ORCA. About 25 minutes.

1 · The entry layout

struct dirent {
    ino_t      d_ino;     // 4 bytes   inode number
    __uint16_t d_reclen;  // 2 bytes   length of THIS entry on disk
    __uint8_t  d_type;    // 1 byte    4 = DIR, 8 = REG, 10 (0x0a) = LNK
    __uint8_t  d_namlen;  // 1 byte    how many name bytes follow
    char       d_name[];  // the name, then padding
};
Four facts that do all the work 1. Little-endian. 64 00 00 00 is 0x64, and 02 00 10 00 is 0x00100002. Read the bytes backwards.
2. Hop by d_reclen. The next entry starts reclen bytes after this one starts. Don't look for it after the name: the padding often holds leftover junk.
3. Inode 0 means deleted. The name bytes are still there, so the same name may show up twice, once deleted and once live.
4. 16 bytes per line. The left column is the offset in hex: line 0000040 starts at byte 0x40 = 64.
Slides 4.5, slides 15–16 and 50 ("inumber 0 is unused… hexdump dumps 16 bytes per line")

In every course dump, reclen = 8 + namlen + 1, rounded up to a multiple of 4. That's the 8-byte header, the name and a terminating zero. So "Rodent" (6) → 15 → 16, and "Guinea pig" (10) → 19 → 20. Use it to check your hops. ext2 also pads entries to 4 bytes. Slides 4.6, "Directory entries are 4-byte aligned"

I25.2 (the Reptile/Sheep/Arctic Fox dump): inode 0x68 is at offset 0x8c, with header 68 00 00 00 14 00 0a 0a. What type is it?

  1. a directory, DT_DIR
  2. a symlink, DT_LNK
  3. a regular, DT_REG
  4. a deleted entry

Byte 7 of the entry (d_type) is 0x0a = 10 = DT_LNK. The next byte, also 0a, is namlen (10 → "Arctic Fox"). Don't mix the two up.

I25.3: "Sparrow" is at offset 0x18 with inode bytes 64 00 00 00. Its inode in hex?

  1. 0x64
  2. 0x64000000
  3. 0x6400
  4. 0x100

Little-endian: read the bytes backwards, 00 00 00 64 = 0x64. (In that dump, "Domestic canary" appears twice: the first copy has inode 0, so the live one is 0x66.)

4 · Resolving a path from a disk picture

The slides' example: inodes are in blocks 100–199, 8 per block, root is inumber 2. Inode n is in block 100 + ⌊n / 8⌋. Opening /usr/lib/libc.a reads 100 (root inode), 200 (root dir), 102 (inode 16), 204 (/usr), 101 (inode 9), 203 (/usr/lib), 106 (inode 55). open stops at the file's inode and doesn't read its data. Slides 4.5, slides 21–37; Tutorial 9 solution

Same layout. Which block holds inode 37?

⌊37 / 8⌋ = 4, so block 100 + 4 = 104 (it's inode 37 mod 8 = 5 within that block).
