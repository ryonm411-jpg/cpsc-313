File Descriptors and the Three Tables

A file descriptor is a small number. To answer any fd question, follow the arrows it starts.

Your win for today: trace the three tables through open, close, fork and dup; answer "which character is read?" (R4.5); and write the two lines of I/O redirection (R4.4). About 25 minutes.

1 · What a file descriptor is

When a process opens a file, the kernel hands back a file descriptor: a small non-negative integer the process uses in every later call. CS:APP §10.3; man open

int fd = open("notes.txt", O_RDONLY);   // e.g. returns 3
char buf[10];
ssize_t n = read(fd, buf, 10);          // reads up to 10 bytes, moves the offset by n
write(1, buf, n);                       // fd 1 is standard output
close(fd);                              // fd 3 is free again

Every process starts with three already open: 0 = standard input, 1 = standard output, 2 = standard error. open always returns the lowest free number, so the first file you open is usually 3.

A process has 0, 1, 2 open, opens a file (gets 3), opens another (gets 4), then closes 3 and opens a third file. What does the last open return?

  1. 5
  2. 3
  3. 4
  4. 0

Lowest free number. 3 was freed by close.

2 · The three tables

TableHow manyEach entry holds
File descriptor tableone per processa pointer to an open-file-table entry
Open file tableone for the whole system; one entry per open() callthe current offset, the mode (read/write), a reference count, and a pointer to the v-node
V-node tableone for the whole system; one entry per filethe file's metadata (an in-memory copy of its inode): size, type, where its blocks are

CS:APP §10.8, Figures 10.12–10.14

The one idea that answers most questions The offset lives in the open-file-table entry. Two fds share an offset exactly when they point to the same open-file-table entry.

Process P calls open("f") twice, then fork(). How many open-file-table entries refer to f?

  1. 1
  2. 4
  3. 2
  4. 3

One per open call = 2. fork adds no entries, it just raises each refcount to 2. There is still one v-node, with refcount 2.

After fd2 = dup(fd1), a read of 5 bytes on fd1 is followed by a read on fd2. Where does the fd2 read start?

  1. 5 bytes after fd1's start
  2. at the start of the file
  3. at fd1's starting offset
  4. at the end of the file

dup shares the open-file-table entry, so it shares the offset.

A process opens f (fd 3) then calls close(3). No one else has f open. What is freed?

  1. Only the fd table entry
  2. The fd and open-file entries
  3. Only the open-file-table entry
  4. All three entries

The open-file refcount hits 0, so it's freed; that drops the v-node refcount to 0, so it's freed too.

4 · "Which character is read?" (R4.5)

The file holds U,K,M,N,W,H,A,E,P,V from offset 1310. A and B each open the file and seek to 1310, so they have two entries and two offsets.

StepA offsetB offsetResult
A reads 11310 → 13111310U
B reads 113111310 → 1311U: B has its own offset
B writes C,S13111311 → 1313bytes 1311–1312 become C,S (K,M overwritten)
A reads 11311 → 13121313C: same file data, so A sees B's write
B reads 113121313 → 1314N
Compare: if B were A's forked child One shared offset: A reads U, B reads K, B writes C,S over M,N, A reads W, B reads H. Always check how the second fd was made first.

Drill: the setup changes between separate open, fork and dup. Type letters.

5 · I/O redirection (R4.4)

command < fileName means "whatever the program reads from standard input (fd 0) should come from fileName". The program just calls read(0, …). The shell's job is to make fd 0 point at the file before running it.

newFD = open(fileName, O_RDONLY);   // mode argument: N/A (only used with O_CREAT)
dup2(newFD, STDIN_FILENO);          // STDIN_FILENO is 0: make fd 0 point where newFD points

Optionally close(newFD) afterwards, since fd 0 now holds its own reference. The order of dup2's arguments is (the fd you have, the fd you want to replace). CS:APP §10.9; man dup

Shell syntaxopen flagsthen
cmd < fO_RDONLYdup2(newFD, 0)
cmd > fO_WRONLY | O_CREAT | O_TRUNC, mode e.g. 0644dup2(newFD, 1)
cmd >> fO_WRONLY | O_CREAT | O_APPEND, modedup2(newFD, 1)
cmd 2> fO_WRONLY | O_CREAT | O_TRUNC, modedup2(newFD, 2)

Which line sends a program's standard output to the file opened as fd?

  1. dup2(1, fd);
  2. dup2(fd, 0);
  3. dup2(fd, 1);
  4. dup(1);

dup2(old, new) makes new a copy of old. We want fd 1 to become a copy of fd. dup2(1, fd) does the reverse: it throws away the file.

For cmd > out.txt, when out.txt doesn't exist yet, which flag is required?

  1. O_RDONLY
  2. O_CREAT
  3. O_APPEND
  4. O_EXCL

Without O_CREAT, open fails on a missing file. With O_CREAT, the third argument (permissions) matters, unlike R4.4's read-only case.
