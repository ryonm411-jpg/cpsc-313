Latency, Throughput & CPI

Three numbers, three different questions: how long does one instruction take, how many finish per second, and how many cycles does each one really cost?

Your win for today: from a register latency and stage delays, compute SEQ and PIPE latency and throughput in two lines. From an instruction mix, compute CPI in one line. That covers Lab 4 L4.1–L4.4 and in-class I11.3, and it's the core of L4.7/L4.8. About 15 minutes.

M is 2 stages ahead of D, so it's 2 lines earlier: Ln_2. (Lesson 5, the staircase.)

  1. 0 cycles
  2. 2 cycles
  3. 3 cycles
  4. 1 cycle

The outcome is known only after Execute, so the pipeline waits 2 cycles. ret costs 3; jmp/call cost 0 (Lesson 2).

1 · One unit trick

1 s = 1012 ps. If one instruction finishes every T ps, that's 1012/T per second = (1000/T) × 109. So:

GIPS in one step throughput (GIPS) = 1000 ÷ (ps per instruction). A 320 ps cycle gives 1000/320 = 3.12 GIPS.

2 · Sequential: one long cycle

SEQ is one big block of combinational logic followed by one register. An instruction goes through all of it in one clock cycle CS:APP 3e §4.4.1, Fig. 4.32:

  • clock = latency = Σ stage delays + register
  • throughput = 1000 / latency (one instruction per cycle)

The book's example: 300 ps of logic + 20 ps register = 320 ps latency and 1000/320 = 3.12 GIPS.

3 · Pipelined: many short cycles

Cut the logic into k stages with a register after each. The clock must fit the slowest stage plus its register CS:APP §4.4.1–4.4.3, Figs. 4.33, 4.36:

  • clock = max stage + register. One instruction retires every clock, so this is also “an instruction retires every ___ ps.”
  • latency = k × clock. Every instruction passes through all k stages, and each stage takes a full clock.
  • throughput = 1000 / clock

SEQ, 300 ps logic320320 ps3.12 GIPS

Read the table for the two big ideas Pipelining makes latency worse (360 > 320), because each instruction now pays for k registers. It still wins on throughput, since k instructions are in flight at once. Deeper means diminishing returns: at 6 stages the 20 ps register is 29% of every clock. Unbalanced stages waste time too, since the fast stages wait for the slow one.

Try it. The register is 20 ps, and there are 4 stages of 80 ps each.

SEQ latency, in ps?

80 × 4 + 20 = 340 ps. One block, one register.

SEQ throughput, in GIPS (2 decimals)?

1000 / 340 = 2.94 GIPS.

PIPE latency, in ps?

Clock = 80 + 20 = 100 ps. Latency = 4 × 100 = 400 ps. Worse than SEQ's 340.

PIPE throughput, in GIPS (2 decimals)?

1000 / 100 = 10.00 GIPS. More than 3× SEQ.

4 · CPI: what hazards cost

Ignoring pipeline fill, an ideal pipeline retires one instruction per cycle (CPI = 1). Every bubble adds a cycle to that CS:APP §4.5.9:

The formula CPI = 1 + Σ (fraction of instructions with that event × its penalty in cycles)
Event (with forwarding)Penalty
load/use hazard (can't be forwarded in time)1
conditional jump, no prediction (every one)2
conditional jump, mispredicted2
ret3
jmp, call, correctly predicted jump0

Watch the nested percentages: “20% of instructions are branches, 60% of those are conditional” means 0.20 × 0.60 = 12% of instructions. The book's example: lp 0.05 + mp 0.16 + rp 0.06, so CPI = 1.27.

Forwarding, no branch prediction. 10% of instructions are branches, 70% of branches are conditional, 12% of instructions have a load/use hazard, 2% are ret. CPI?

1 + 0.12 × 1 + (0.10 × 0.70) × 2 + 0.02 × 3 = 1 + 0.12 + 0.14 + 0.06 = 1.32.

5 · Putting them together: what actually makes a program fast

The iron law time = instructions × CPI × clock period

Most “always / sometimes / never” questions are traps where one factor improves and another gets worse. Check each factor separately:

  • SEQ: CPI is exactly 1 by design. One instruction per (long) cycle, never more, never fewer.
  • Any pipeline, ignoring fill: at most one instruction retires per cycle, so cycles ≥ instructions (CPI ≥ 1). It's equal only when no bubble is ever inserted.
  • More stages: a shorter clock (the first factor improves), but the stall and misprediction penalties grow in cycles (the CPI factor gets worse). Which effect wins depends on the program.
How this course grades these (Lab 4 answer key) will always / will never only when it's true by definition (e.g. SEQ uses exactly one cycle per instruction). is likely / unlikely to for design trends that usually hold but aren't guaranteed for any two implementations. A pipeline's clock is likely shorter than SEQ's, and more stages likely means a shorter clock. None when the answer is “could be equal, could be more” and there's no “at least as many” option: a hazard-free program gives cycles = instructions, so “all programs take more cycles” fails.

On PIPE with forwarding, can a program that has a data hazard run in exactly as many cycles as instructions (ignoring fill)?

  1. No, never possible
  2. Yes, it is possible
  3. Only without jumps
  4. Only with load/use

Yes. addq %rax,%rbx then subq %rbx,%rcx is a data hazard, and forwarding e_valE removes it with 0 bubbles. Only load/use (or control hazards) still add cycles. Not every hazard costs a cycle; only the bubbles count.

Design A has a 100 ps clock and runs a program at CPI 1.5. Design B has a 120 ps clock and runs it at CPI 1.2. Which finishes first?

  1. A, shorter clock
  2. A, by 6 ps per instruction
  3. They finish together
  4. B, by 6 ps per instruction

A: 1.5 × 100 = 150 ps per instruction. B: 1.2 × 120 = 144 ps. B wins despite the slower clock. That's the trap in “a shorter cycle time always means faster.”
