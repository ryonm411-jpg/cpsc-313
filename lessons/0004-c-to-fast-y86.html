With forwarding and BTFNT prediction, what does each of these cost? ret · a forward je that is taken · call

  1. 3 · 0 · 3
  2. 3 · 2 · 0
  3. 2 · 2 · 0
  4. 3 · 0 · 0

ret: 3, because the return address comes from memory. A forward jump is predicted not taken, so when it is taken, 2 instructions get squashed. call: 0, because the target is a constant in the instruction. Lesson 2.

1 · The only equation you need

On the pipeline, each instruction costs one cycle, and each bubble costs one more CS:APP §4.5.9:

cycles ≈ instructions + bubbles = instructions × CPI

So there are two levers: (a) fewer bubbles (lower CPI) and (b) fewer instructions. They are independent. Removing a cheap, never-stalling instruction raises CPI, because the bubbles that remain are spread over fewer instructions, but the program still gets faster.

Version X: 119 instructions, CPI 1.38. Version Y: 128 instructions, CPI 1.35. Which one finishes first?

  1. X, by about 9 cycles
  2. Y, by about 9 cycles
  3. Y, by about 3 cycles
  4. they tie, more or less

X ≈ 119 × 1.38 ≈ 164, Y ≈ 128 × 1.35 ≈ 173. X wins despite the worse CPI. Judge by cycles, never by CPI alone. (These are real numbers from later in this lesson.)

2 · Find the bubbles in the recursive version

long sum(long *a, long n) {
    return n == 0 ? 0 : *a + sum(a+1, n-1);
}
sum:
  andq   %rsi, %rsi
  je     base             # goto base if n == 0
  mrmovq (%rdi), %r8
  pushq  %r8              # save *a on stack
  irmovq $8, %r8
  addq   %r8, %rdi
  irmovq $1, %r8
  subq   %r8, %rsi
  call   sum              # rax = sum(a+1, n-1)
  popq   %r8
  addq   %r8, %rax        # rax = *a + sum(a+1, n-1)
  ret
base:
  irmovq $0, %rax
  ret

Trace it by hand first, with forwarding + BTFNT. Go one line at a time and ask: is this a load used next? A jump that's mispredicted? A ret?

In a call with n > 0, which instructions cause bubbles? (select all)

  1. je base
  2. pushq %r8
  3. call sum
  4. addq %r8, %rax
  5. ret
  6. subq %r8, %rsi

pushq %r8: load/use. It needs the %r8 that mrmovq is still loading → 1 bubble.
addq %r8, %rax: load/use. popq %r8 gets its value from memory (valM) → 1 bubble.
ret: 3 bubbles, every single call.
je base is a forward jump, predicted not taken. That's right in every call with n > 0, and wrong only once, in the base case (2 squashed). call is free. subq gets %r8 from e_valE.

So each call with n > 0 costs 1 + 1 + 3 = 5 bubbles. The base case costs 2 + 3 = 5 as well.

For n = 10 (10 calls with n > 0, plus the base case), how many bubbles in total?

55 = 10 × 5 + 5. That's 20 data bubbles + 33 from the 11 rets + 2 squashed. The bench below shows the same numbers (with a tiny 4-instruction main that adds no bubbles). The recr-start.s in your repo has its own main, so its totals may be off by a few. The per-call costs are the same.

Now fix it yourself

Open the bench, press Duplicate as new version on “recursive (given)”, and make small, local edits. Keep the stack and the recursion. Check that the ✓ stays green after every change. Try the hints one at a time, only when you're stuck.

Hint 1: the first load/use

The mrmovq→pushq stall needs one independent instruction in between. irmovq $8, … is independent, but it clobbers %r8… so load into a different register.

Hint 2: an instruction you don't need

subq sets the condition codes too. If you decrement n first, is n − 1 < 0 the same test as n == 0 (for n ≥ 0)? Then andq is redundant.

Hint 3: what you can't fix locally

The popq→addq stall has nothing independent to put between them, and every ret costs 3. No small edit removes those. Remember this. It's the argument for part 3.

3 · Recursion → loop

long sum(long *a, long n) {
  int s = 0;
  for (long *p = a; p < a + n; p++)
    s += *p;
  return s;
}

The relationship: both compute a[0] + a[1] + … + a[n−1]. The recursion adds from the right: a[0] + (a[1] + (… + 0)). Each + waits for the call below it to return, so every element needs its own stack frame. The loop adds from the left, into one running total. Since + is associative, the answers are the same. The bridge between them is tail recursion: rewrite the recursion as sum(a+1, n-1, s + *a), so nothing is left to do after the call, and the call becomes a jump back to the top. That's a loop. (Small C quirk: int s is 32 bits. y86 only has 64-bit arithmetic, so a direct translation keeps s as 64 bits.)

Why should a direct translation of the loop beat the recursion on the pipeline? (select all)

  1. no ret per element
  2. no push/pop per element
  3. it forwards values better
  4. its branch is well predicted

Per element, the recursion spends ~12 instructions and 5 bubbles (3 of them on ret). A loop needs ~6 instructions: no call/ret/push/pop. Its backward loop branch is predicted taken and is wrong only on the final exit. Forwarding works the same in both. The loop just gives it fewer hazards to deal with.

Write it

In the bench, add a version and write the loop yourself. Arguments: %rdi = a, %rsi = n. Return the result in %rax. The label must be sum:. Only if you're stuck, open the direct translation below (your repo's loop-start.s is another one).

One direct translation (try first!) 
sum:
  irmovq $0, %rax        # s = 0
  irmovq $8, %r8
  rrmovq %rsi, %rdx
  mulq   %r8, %rdx       # 8n
  addq   %rdi, %rdx      # end = a + n  (pointer arithmetic: bytes)
  jmp    test
loop:
  mrmovq (%rdi), %r9
  addq   %r9, %rax       # s += *p
  addq   %r8, %rdi       # p++
test:
  rrmovq %rdi, %r10
  subq   %rdx, %r10      # p - end
  jl     loop            # while p < end  (backward → predicted taken)
  ret

Measure it, then answer the last part of the tutorial: where are the unnecessary stalls? Press stalls on its row.

For the direct translation above (n = 10), how many bubbles are data stalls that a reorder could remove?

10. mrmovq (%rdi), %r9 → addq %r9, %rax is a load/use, and it happens on every iteration. Move addq %r8, %rdi between them and all 10 disappear. The other 5 bubbles (one mispredicted exit + one ret) are as low as they go.

Then go further, now pulling the instruction-count lever. Can the loop test become free? Count n down with subq and branch on the flags it sets, instead of computing p − end every iteration. That's Hint 2 again, in loop form.

The “count down” loop (5 instructions per element):

sum:
  irmovq $0, %rax
  irmovq $8, %r8
  irmovq $1, %r9
  andq   %rsi, %rsi
  jle    done            # n <= 0: nothing to add
loop:
  mrmovq (%rdi), %r10
  addq   %r8, %rdi       # fills the load/use slot
  addq   %r10, %rax
  subq   %r9, %rsi       # n--, and sets the flags for jg
  jg     loop
done:
  ret
