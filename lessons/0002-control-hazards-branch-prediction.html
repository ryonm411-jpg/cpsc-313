Control Hazards & Branch Prediction

Fetch has to pick the next address every cycle, sometimes before anyone knows what it is.

Your win for today: count the total stall + squash cycles for a short y86 program under any setting (forwarding on or off; no prediction, never taken, always taken, or backward-taken/forward-not-taken). That's exactly the I10.1 / I10.2 / P9.2 question type. About 20 minutes.

Warm-up: interleaved recall from Lesson 1

With forwarding, how many stalls, and from where does andq get %r8?

mrmovq 0x10(%rdi), %r8
andq   %r8, %r9
  1. 0 stalls, e_valE
  2. 0 stalls, m_valM
  3. 1 stall, m_valM
  4. 2 stalls, W_valM

Load/use at distance 1. The loaded value exists only at the end of Memory, so one bubble is unavoidable. After that, andq is in Decode while mrmovq is in Memory → m_valM. Lesson 1 §4.

1 · Who doesn't know the next PC?

Each cycle, Fetch must choose the next instruction's address. Most instructions make that easy: next PC = valP (the address right after). The trouble comes from instructions that change control flow slides 2.4, “Dealing with Control Hazards”:

jmp, callin Fetch0the target is valC, a constant inside the instruction bytes

jXX (conditional)after Execute2 cycles if we waitthe condition codes are checked in Execute (e_Cnd). The right instruction is fetched when jXX is in Memory.

Above: ret holds up the next fetch until it reaches W: 3 lost cycles.

Not control hazards cmovXX never changes the PC. It's a conditional data move, so it's handled like any other ALU result (valE + forwarding). Branch prediction has nothing to do with it. Same for rmmovq, OPq, and so on.

Which can cause a control hazard? (select all)

  1. jle
  2. jne
  3. cmovge
  4. ret
  5. rmmovq

Conditional jumps (outcome unknown until Execute) and ret (target unknown until Memory). cmovge moves data conditionally but the next PC is still valP. rmmovq only writes memory.

2 · Guess, then fix it if wrong

Instead of stalling 2 cycles on every jXX, Fetch predicts and keeps going slides 2.4, “Branch prediction”:

  • Never taken: guess next PC = valP (fall through).
  • Always taken: guess next PC = valC (the jump target). Both are available in Fetch, so either guess costs nothing to make.
  • Backward taken, forward not taken (BTFNT): a backward jump is usually a loop, so guess taken. A forward jump is usually an if, so guess not taken.

If the guess was right: 0 lost cycles. If wrong: by the time Execute finds out, 2 wrong-path instructions are already in Fetch and Decode. The hardware squashes them (turns them into bubbles/nops) and fetches the right one. That costs 2 cycles, the same as not predicting at all. So prediction never makes things worse.

Above: never-taken prediction, but je is taken. The two struck-through instructions are squashed.

To recover from a wrong “taken” guess, the pipeline must remember the fall-through address. That's why valP travels down the pipeline with the jump, as M_valA slides 2.4, “What if we mispredict?”.

Which guess is best?

From the slides: always taken is right ≈60% of the time, never taken ≈40%, BTFNT ≈65%. Real CPUs spend a lot of hardware here, e.g. 1-bit predictors (“do what this branch did last time”) and per-PC tables. Linux even lets programmers give hints with likely()/unlikely(). For one specific program, though, count it: the best predictor is the one that's right for the branch that runs the most.

This loop's jg loop runs 10 times: taken 9 times, then not taken once. Which predictor loses fewer cycles?

  1. Never taken
  2. Always taken
  3. No prediction
  4. All equal

Always taken mispredicts only the final exit: 1 × 2 = 2. Never taken mispredicts all 9 taken iterations: 18. No prediction stalls on every execution: 10 × 2 = 20. A backward loop branch is the classic always-taken case. If the loop instead exits with a forward jge loop_end that's only taken once, the answer flips. Check which way the jump goes!

3 · The counting procedure

This handles every I10-style question:

  1. Trace the values. Compute registers and the condition codes (set by the last OPq) so you know the actual outcome of each jXX. Unset registers are 0. Watch for divq/mulq/andq/xorq: -8 / -19 = 0 (truncates), so ZF=1.
  2. Walk only the executed path, in order.
  3. Data hazards: for each instruction, find the most recent writer of each source register and apply Lesson 1's distance table. With forwarding, only load/use at distance 1 costs anything (1). Without, 3/2/1 stalls at distance 1/2/3.
  4. Control: each jXX costs 2 if there's no prediction or the guess is wrong, else 0. Each ret costs 3. jmp/call cost 0.
  5. Add it up. CPI = (instructions executed + 4 + lost cycles) / instructions executed, counting the final halt and not counting squashed instructions. The 4 cycles fill the pipeline: the course's slides 2.5 include them (71/37), so include them unless the question says to ignore startup.
Subtlety: stalls overlap Without forwarding, a stall on one instruction also gives later instructions extra time. So the distance-table numbers can't simply be added when hazards are close together. Measure distance in cycles, not just instructions. If in doubt, draw the diagram (or paste the code into the sandbox below).

Worked example

irmovq $5, %rcx

4 · Transfer: reason about a new instruction

Exam questions often invent an instruction and ask you to reason about it. Use the same question as before: at what stage is the next PC first known?

A made-up jmpR rB jumps to the address held in register rB. With full forwarding, where is the target first available?

  1. Fetch
  2. Decode
  3. Execute
  4. Memory

Registers are read (or forwarded) in Decode. The target isn't in the instruction bytes, so Fetch can't know it. But it doesn't need the ALU or memory either. So Fetch has to wait for jmpR to finish Decode. Work out how many cycles that costs compared to jmp (0) and ret (3), then ask me if you want to check your reasoning.
