C ⇄ Y86, and "Did It Change?"

Read any Y86 loop and name its shape. Translate both directions. And catch the trap question: the assembly that almost matches the C but has one thing flipped.

Your win for today: a reliable method, not vibes. When you're asked "is this a for/while/do-while, or neither, or was it changed?", you'll back-translate the assembly into C line by line and compare. That one habit fixes most of these questions.

The seven Y86 moves you'll see in C code

Almost every compiled C statement is one of these. Keep the y86 Reference open and match each asm line to its meaning:

C ideaY86Meaning (shorthand)
constant into a variableirmovq $5, %raxR[rax] = 5
copy a variablerrmovq %rax, %rbxR[rbx] = R[rax]
arithmetic x = x OP yaddq %rsi, %rdiR[rdi] = R[rdi] + R[rsi]
read memory / *p / a[i]mrmovq 8(%rbx), %raxR[rax] = M[R[rbx] + 8] (load)
write memory / *p = vrmmovq %rax, 8(%rbx)M[R[rbx] + 8] = R[rax] (store)
compare / testsubq %rsi, %rdi or andq %rdi, %rdisets condition codes
branchjle L, jg L, jmp Lgo to L (maybe conditionally)
The direction trap that costs the most marks

mrmovq D(rB), rA is a LOAD (memory → register): R[rA] = M[D + R[rB]]. The memory operand is on the left.

rmmovq rA, D(rB) is a STORE (register → memory): M[D + R[rB]] = R[rA]. The memory operand is on the right.

Read the mnemonic letters: mrmovq = memory to register; rmmovq = register to memory. The register operand is always written as a bare %reg; the memory operand always has the D(%reg) form.

Four Y86 limits that force the C apart

Y86 is deliberately small. These limits explain why one C line often becomes several asm lines — and they're favourite "why can't this be one instruction?" questions:

  1. No memory-to-memory. a[i] = b[j] must load into a register, then store. Two instructions.
  2. No immediate-to-memory. *p = 5 needs irmovq $5, %rtmp then rmmovq %rtmp, (p). You can't write a constant straight to memory.
  3. No cmpq / testq in base Y86. To compare, you run an OPq that sets the flags. The usual tricks: subq %ry, %rx (flags on x − y, but it overwrites %rx), or andq %rx, %rx (flags on x, leaves %rx alone — the Y86 way to "test" a value against 0).
  4. Only OPq sets condition codes. mrmovq, rmmovq, irmovq, rrmovq do not. So a jle reads the flags from the most recent addq/subq/andq/..., not from the move just above it.

Part A · Loop shapes: where is the test?

This is the heart of "is it a for, while, or do-while?". The compiler expresses all of them with jumps, and the shape is decided by where the conditional branch sits:

ShapeStructure in asmBody runsTell
do-whilebody … then a conditional jump back up to the body≥ 1 timeNo guard before the loop. The only branch is at the bottom, jumping backward.
while / for ("jump-to-middle")jmp test → body → test: → conditional jump back up0 or moreAn unconditional jmp to the test before the body. That initial jump is the guard.
while / for ("guarded do")test at top, conditional jump past the loop; body; jump back to test0 or moreA conditional jump forward (out of the loop) at the top.
The one question to ask "Can the body be skipped entirely?" If there is a check before the body can run (an initial jmp test, or a guard that jumps past the loop), the body can run zero times → it's a while or for. If the body always runs once before any check, it's a do-while.

for vs. while is a finer call — both can compile to the exact same jump-to-middle shape. The difference is bookkeeping: a for has a dedicated init (before the loop) and an update step at the bottom of the body (e.g. i++). If you see an obvious counter being incremented at the end of each iteration plus an init before, lean for; a while is just the condition. On this quiz the examinable distinction is almost always do-while vs. while/for — the "runs ≥1 vs. can run 0" split.

Worked example: back-translate a loop

Arguments follow the calling convention: %rdi = pointer a, %rsi = count n, return in %rax.

sum:
    irmovq $0, %rax        # s = 0
    irmovq $8, %r8         # stride (8 bytes per long)
    irmovq $1, %r9         # constant 1
    andq %rsi, %rsi        # set flags from n  (n & n = n, n unchanged)
    jle done               # if n <= 0, skip the loop entirely
loop:
    mrmovq (%rdi), %rdx    # %rdx = *a
    addq %rdx, %rax        # s += *a
    addq %r8, %rdi         # a++   (pointer moves 8 bytes)
    subq %r9, %rsi         # n--   (and sets flags on the new n)
    jg loop                # if n > 0, repeat
done:
    ret

Back-translate it mechanically, then read off the C:

  • The andq %rsi,%rsi; jle done before loop: is a guard → the body can run 0 times → this is a while/for, not a do-while.
  • Body: s += *a; a++; n--. The test that repeats is n > 0.
long sum(long *a, long n) {
    long s = 0;
    while (n > 0) {     // equivalently: for (; n > 0; n--)
        s += *a;
        a++;
        n--;
    }
    return s;
}

In that sum, you remove the two lines andq %rsi, %rsi and jle done (so execution falls straight into loop:). What has the loop become?

  1. Still a while — no change in behaviour
  2. A do-while: the body now always runs at least once, which is wrong if n can be 0
  3. An infinite loop
  4. A for loop counting up

With the guard gone, nothing checks n before the first iteration. The body runs once and only then hits subq/jg. That's exactly a do { … } while (n > 0). If called with n = 0 it reads *a and decrements n to −1, looping a huge number of times — the classic "they changed a while into a do-while" bug.

Part B · "Did it change?" — the back-translation checklist

When the quiz gives you C and assembly and asks whether the asm faithfully implements it, don't eyeball it. Translate each asm line into shorthand, then check these six spots where graders plant changes:

The six things that get flipped
  1. Operator. addq ↔ subq, mulq ↔ addq. Does the C say + but the asm subq?
  2. Operand order on subq. subq %rA, %rB is R[rB] = R[rB] − R[rA]. Backwards order computes the negation of what you want.
  3. Load vs. store. mrmovq (load) swapped for rmmovq (store), or the operands swapped.
  4. The condition. jle vs jl vs jg vs jge — an off-by-one in the comparison (< became <=).
  5. The displacement / index. 8(%rbx) vs 16(%rbx) — reading the wrong array element.
  6. The register. A result written to %rcx but the next line reads %rdx.

The jXX conditions (read them off the reference)

After subq %rA, %rB the flags describe R[rB] − R[rA], so the jump tests rB vs rA:

JumpTaken whenAfter subq %rA,%rB means
jeresult = 0rB == rA
jneresult ≠ 0rB != rA
jlresult < 0rB < rA
jleresult ≤ 0rB <= rA
jgresult > 0rB > rA
jgeresult ≥ 0rB >= rA

The C is if (x < y) return 1; with x in %rdi, y in %rsi. Which asm faithfully implements the comparison?

  1. subq %rdi, %rsi ; jl yes
  2. subq %rsi, %rdi ; jg yes
  3. subq %rsi, %rdi ; jl yes
  4. subq %rdi, %rsi ; jge yes

We want to test x < y, i.e. rdi < rsi. From the table, rB < rA after subq %rA,%rB, so put x=rdi in rB and y=rsi in rA: subq %rsi, %rdi (flags on x − y), then jl. Option 1 compares y − x; option 2 flips the condition; option 4 is the negation.

The C is a[2] = a[0]; where a (a long*) is in %rbx. Which asm is correct?

  1. mrmovq (%rbx), 16(%rbx)
  2. rmmovq (%rbx), %rax ; mrmovq %rax, 16(%rbx)
  3. mrmovq 16(%rbx), %rax ; rmmovq %rax, (%rbx)
  4. mrmovq (%rbx), %rax ; rmmovq %rax, 16(%rbx)

a[0] is at (%rbx), a[2] is at 16(%rbx) (2 × 8 bytes). You must load a[0] into a register then store it — Y86 has no memory-to-memory move (option 1 isn't even a legal instruction). Option 2 uses rmmovq/mrmovq backwards. Option 3 copies the wrong direction (a[0] = a[2]).

C: for (i = 0; i < n; i++) sum += i; The asm uses subq %rsi, %rcx (with %rcx=i, %rsi=n) followed by jl loop to repeat. What's wrong?

  1. subq %rsi, %rcx overwrites %rcx (i), corrupting the counter — you must compare with a scratch copy or use andq/a non-destructive scheme
  2. Nothing — this is correct
  3. jl should be jg but the subtract is fine
  4. You can't use %rcx as a loop counter in Y86

subq %rsi, %rcx computes i − n and writes the result back into %rcx, destroying i. This is the #1 Y86 comparison bug. To compare without clobbering, copy first (rrmovq %rcx, %rdx; subq %rsi, %rdx) or restructure as a count-down using subq $1 on the counter where destroying-into-the-next-value is intended.

Part C · C → Y86 from scratch

Writing Y86 from C is the same seven moves in reverse. A recipe:

  1. Put each C variable in a register (follow the convention for parameters: %rdi, %rsi, %rdx, %rcx, %r8, %r9; result in %rax).
  2. Each *p / a[i] read → mrmovq; each write → rmmovq. Compute addresses with D(%reg) or by walking a pointer with addq.
  3. Each OP → the matching OPq (remember it's rB = rB OP rA).
  4. Each condition → an OPq to set flags (subq or andq) + a jXX. Pick the jump from the table above.
  5. Constants need irmovq first — you can't add/store an immediate directly.

Worked example

long f(long x) {        // x in %rdi, return in %rax
    if (x > 0) return x * 2;
    return 0;
}
f:
    irmovq $0, %rax        # default return 0
    andq %rdi, %rdi        # set flags from x
    jle done               # if x <= 0, return 0
    irmovq $2, %rcx
    rrmovq %rdi, %rax       # rax = x
    mulq %rcx, %rax         # rax = x * 2    (rax = rax * rcx)
done:
    ret

Translate *p += 10; where p is in %rdi. Which sequence is correct and legal in Y86?

  1. addq $10, (%rdi)
  2. mrmovq (%rdi), %rax ; irmovq $10, %rcx ; addq %rcx, %rax ; rmmovq %rax, (%rdi)
  3. mrmovq (%rdi), %rax ; addq $10, %rax ; rmmovq %rax, (%rdi)
  4. irmovq $10, %rax ; rmmovq %rax, (%rdi)

You can't add to memory directly (option 1) and you can't add an immediate (addq $10 isn't legal — addq takes two registers; option 3). You must: load, put 10 in a register, add register-to-register, store. Option 4 just overwrites *p with 10.
