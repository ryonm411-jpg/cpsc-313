CPSC 313 · Quiz 1 · "Can SEQ run this new instruction?"

New-Instruction Feasibility Drill

Ten questions in the exact shape of the addm one you pasted. Each asks: given the SEQ datapath, can this brand-new instruction run as a single instruction — and if not, which specific resource is missing? "Too complicated" earns nothing; name the wire.

The hardware budget — one of each

Every SEQ instruction gets, at most, this much hardware. An instruction is feasible iff it fits inside this budget. If it needs more, say exactly what.

  • Fetch — one constant valC (only if the encoding has room for it).
  • Decode — two register reads, into valA and valB. (The same register may be read into both.)
  • Execute — one ALU operation, producing one valE. The A input is valA, valC, or ±8; the B input is valB or 0. So valB+valC, valB−valA, valA+0, valB±8 are fine — but not valA+valC (both on the A side), and nothing can use valM (it doesn't exist yet).
  • Memory — one access. Address is valE or valA. Data written is valA or valP (never valC, never valM).
  • Writeback — two write ports: port E writes valE, port M writes valM. (So writing two registers is fine — that's what popq does.)
  • PC update — picks one of valP, valC, valM (optionally chosen by Cnd).
The three-question method
  1. How many ALU operations does it need? More than one add/subtract that depends on a different value → no (one ALU).
  2. Does any step need valM fed somewhere other than a register or the PC? (e.g. back into the ALU, or into another memory access) → no (valM appears only after Execute, and only reaches writeback or PC update).
  3. Does the value it needs actually have a wire to where it's going? valC→memory-data, register→PC, valA→write-port: none of those wires exist.

Writing two registers, reading the same register twice, and PC = valM are all allowed — those are the traps that look impossible but aren't (popq, ret).

The questions

Each grades itself. After you answer, open "Why" and make sure your reason matches — on the quiz you must name the resource, not just pick yes/no.

Q1. leaq D(rB), rA — compute an address without touching memory: R[rA] = R[rB] + D. Feasible in SEQ?

  1. Yes — Execute computes valE = valB + valC, and Writeback sends valE to rA through port E. No Memory access at all.
  2. No — any instruction that computes an address must go through the Memory stage.
  3. No — valC can't be an input to the ALU.
  4. Yes, but only if D is 0 or ±8.

It's exactly mrmovq minus the memory read: valE = valB + valC (one ALU op), then R[rA] = valE via port E. Nothing forces an instruction to use Memory. valC is a legal ALU A-input, so option 3's restriction is false.

Q2. negq rB — negate in place: R[rB] = −R[rB]. Feasible?

  1. No — the ALU can add or subtract two values, but it can't subtract a register from a constant.
  2. Yes — read the register into valA, force the ALU's B input to 0, and compute valE = 0 − valA; write valE back to rB.
  3. No — negation needs a dedicated negate unit that SEQ doesn't have.
  4. Yes, but it needs two register reads to do it.

0 is a legal ALU B-input and subtract is a legal ALU op, so valE = 0 − valA = −R[rB] in a single Execute. One read, one ALU op, one write — comfortably inside budget.

Q3. doubleq rB — R[rB] = 2 × R[rB]. Feasible?

  1. Yes — Decode reads R[rB] into both valA and valB, and Execute computes valE = valB + valA.
  2. No — Decode can't route the same register to both read ports.
  3. No — multiplying by 2 needs a shifter, which the ALU isn't.
  4. Yes, but only via valE = valB + 8.

The two read ports are independent; both can name rB. Then valE = valB + valA = R[rB] + R[rB] is one ordinary ALU add. (×2 happens to equal a left-shift, but you don't need one.)

Q4. jmem D(rB) — indirect jump: set PC = M[D + R[rB]] (jump to the address stored in memory). Feasible?

  1. No — PC update can only take valP or valC; a value read from memory can never become the PC.
  2. No — it needs the ALU twice: once for the address, once to load the PC.
  3. Yes — valE = valB + valC addresses memory, valM = M8[valE] is read, and PC update selects valM — exactly how ret works.
  4. Yes, but only for a backward jump.

This looks illegal but isn't: ret already does PC = valM. One ALU op for the address, one memory read, and PC update picks valM. All three are wired. The predictor would mispredict it (like ret), but that's a performance issue, not a feasibility one.

Q5. ldinc (rB), rA — load with post-increment: R[rA] = M[R[rB]] and R[rB] = R[rB] + 8. Feasible?

  1. No — writing both rA and rB needs two register writes, and SEQ has only one write port.
  2. No — it needs the ALU twice: once for the load address, once for the +8.
  3. Yes — use valA = R[rB] as the read address, and valE = valB + 8 as the new pointer; port M writes valM to rA, port E writes valE to rB. It's popq's shape.
  4. Yes, but only when rA and rB are the same register.

The load address is the old pointer, available directly as valA — so the one ALU op is free to compute the +8. Two register writes are fine: that's precisely what popq does (R[%rsp] via port E, R[rA] via port M). Option 1's "one write port" is the trap.

Q6. stinc rA, (rB) — store with post-increment: M[R[rB]] = R[rA] and R[rB] = R[rB] + 8. Feasible? (Compare carefully with Q5.)

  1. Yes — it's the mirror image of the load version in Q5, so the same wiring works.
  2. No — the data to store must travel on valA, so the address can only come from valE; that leaves no ALU result for the +8. It would need the ALU twice.
  3. No — you can't read and write memory in the same instruction.
  4. Yes — valE = valB + 8 serves as both the store address and the new pointer.

The asymmetry with Q5 is the whole point. A store's data input must be valA, so valA = R[rA] is taken — the address must be valE. But then valE has to be the address (valB + 0) and the increment (valB + 8) at once: impossible with one ALU. Option 4's trap: valB + 8 is the right new pointer but the wrong store address (off by 8).

Q7. iaddq $V, rB — add an immediate: R[rB] = R[rB] + V. Feasible?

  1. No — OPq-style instructions can never carry an immediate.
  2. Yes — give it a valC field like irmovq (a 10-byte encoding); then valE = valB + valC and R[rB] = valE.
  3. No — the only constants wired to the ALU are 0 and ±8, so V can't reach it.
  4. Yes, but only for V ∈ {1, 8}.

valC is a legal ALU A-input (that's how rmmovq/mrmovq add their displacement). Once the encoding carries valC, valE = valB + valC fits. Option 3 is true only for a 2-byte encoding with no valC — the fix is to add the valC field. (This is CS:APP's famous iaddq homework instruction.)

Q8. incq rB — R[rB] = R[rB] + 1, encoded in just 2 bytes (icode + rA:rB, no constant field). Feasible as given?

  1. Yes — valE = valB + 1.
  2. No — with no valC field, the only constants wired into the ALU are 0 and ±8; there is no 1 to add. (Give it a valC field and it becomes iaddq $1, rB, which fits.)
  3. No — incrementing a register requires a Memory access.
  4. Yes — valE = valB + valC.

Contrast with Q7: the operation is trivial, but a 2-byte encoding has no place to put the 1, and the ALU's hard-wired constants are only 0 and ±8. Option 4 assumes a valC this encoding doesn't have. The engineering fix is exactly Q7.

Q9. swapq rA, rB — exchange two registers: R[rA] ↔ R[rB]. Feasible?

  1. Yes — write R[rA] = valB and R[rB] = valA directly through the two ports.
  2. No — the two write ports carry only valE and valM; valA and valB have no wire to a write port, and valM can only come from a memory read.
  3. Yes — do it with two ALU passes, one per value.
  4. No — because it reads two registers.

Two writes are fine (Q5), but what you can write is fixed: port E = valE (an ALU result), port M = valM (a memory read). The ALU can carry one value through valE, but the second value would have to arrive as valM — and nothing reads memory here. So one of the two writes has no legal source. Reading two registers (option 4) is perfectly normal.

Q10. pushv $V — push an immediate constant: R[%rsp] = R[%rsp] − 8, then M8[R[%rsp]−8] = V. Feasible?

  1. Yes — valE = R[%rsp] − 8, then M8[valE] = valC.
  2. No — you can't decrement %rsp and use it in the same instruction.
  3. No — the address part is fine (valE = valB − 8), but Memory can only write valA or valP; valC has no wire to the memory data input. It needs a new wire, valC → Data.
  4. Yes — it's identical to call.

The stack arithmetic is exactly pushq/call (valE = valB − 8, decrement-and-use is normal). What fails is the data: the memory write port accepts only valA (a register value) or valP (which is why call can push a return address). valC isn't routed there. Spot the pattern: the arithmetic fits, but a wire is missing.

Two to write out (paper)

For the quiz you may be asked to produce the SEQ stage table for a feasible new instruction, not just judge it. Do these on paper, then check.

W1. Write the full SEQ stage notation for the feasible leaq D(rB), rA from Q1.

Reveal 
Fetch:     icode:ifun = M1[PC]
           rA:rB      = M1[PC+1]
           valC       = M8[PC+2]
           valP       = PC + 10
Decode:    valB = R[rB]
Execute:   valE = valB + valC
Memory:    —            (no access)
Writeback: R[rA] = valE
PC update: PC = valP

10-byte encoding (there's a valC, so it starts at PC+2 and the instruction is 10 bytes). No Memory stage, one write via port E. It's mrmovq with the memory read deleted.

W2. Write the SEQ stage notation for the feasible ldinc (rB), rA from Q5 (the popq-shaped load).

Reveal 
Fetch:     icode:ifun = M1[PC]
           rA:rB      = M1[PC+1]
           valP       = PC + 2
Decode:    valA = R[rB]          # old pointer -> used as the read address
           valB = R[rB]          # same register into the other port
Execute:   valE = valB + 8       # the new pointer
Memory:    valM = M8[valA]       # read at the OLD pointer, not valE
Writeback: R[rB] = valE          # port E
           R[rA] = valM          # port M
PC update: PC = valP

The twin of popq rA (which is ldinc (%rsp), rA with the increment baked in). The key move is reading the base register into both ports so the ALU is free to compute +8 while the memory read uses the old value as its address.

Scoring

What to check

Count your reasons, not just the yes/no. Feasible: Q1, Q2, Q3, Q4, Q5, Q7. Infeasible: Q6, Q8, Q9, Q10. The three recurring killers are: a second ALU operation (Q6), a missing wire (Q9 to a write port, Q10 valC→Data), and a constant with nowhere to live (Q8). The three traps that look impossible but pass: two register writes (Q5), reading one register twice (Q3), and PC = valM (Q4).
