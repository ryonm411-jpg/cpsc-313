Stack Frames, Arrays & "Where Does the Write Land?"

The frame layout, how to set one up and tear it down, and the address-arithmetic question that got you last time: given a base pointer in %rbx and an array, work out which instruction to insert, what it is, and the exact hex address it writes to.

Your win for today: one formula — address = base + index × 8 — done in hex, plus a clear mental picture of where the saved registers and return address sit relative to a local array. That's the whole "smash" question.

Part A · The stack grows down

The Y86 stack grows toward lower addresses. pushq subtracts 8 from %rsp then writes; popq reads then adds 8. So the top of the stack (most recently pushed) is at the lowest address, and older data is at higher addresses.

What call and ret do (from the reference)
  • call D = pushq PC (the return address, i.e. address of the next instruction) ; jmp D. It drops %rsp by 8 and stores the return address there.
  • ret = popq PC. It reads the return address from M[%rsp] and jumps to it, raising %rsp by 8.

So the return address lives on the stack at whatever %rsp was right after the call. Anything the callee pushes afterward sits below it (lower addresses).

Prologue and epilogue (frame setup / teardown)

A function that uses a frame pointer and local space does this. %rbp is the callee-saved frame pointer; %rsp is the stack pointer.

Setup (prologue)Effect
pushq %rbpsave caller's frame pointer (it's callee-saved)
rrmovq %rsp, %rbpthis frame's base pointer = current top
irmovq $32, %rax ; subq %rax, %rspallocate 32 bytes of locals (no subq $imm, so load the size first)
Teardown (epilogue)Effect
rrmovq %rbp, %rspfree all locals at once (restore %rsp to the saved-%rbp slot)
popq %rbprestore caller's frame pointer
retpop the return address into the PC

Why is the local size loaded into a register before subq %rax, %rsp instead of writing subq $32, %rsp?

  1. Because %rsp can't be a destination
  2. Because subtraction grows the stack the wrong way
  3. Because Y86 OPq takes two registers — there is no immediate form of subq
  4. It's just a style choice; subq $32, %rsp also works

Y86's OPq instructions (addq, subq, …) only operate register-to-register. To use a constant you first materialise it with irmovq. Same reason you can't write addq $1, %rcx.

Part B · Array addressing — the one formula

The formula For a long array (8 bytes each) whose element 0 is at base: 
address of a[i] = base + i × 8
In Y86 that's (i×8)(%base) as a displacement, or you walk a pointer with addq. Do the i × 8 and the base + in hexadecimal, because addresses are hex.

Hex × 8 and hex + , fast

You'll multiply a small index by 8 and add it to a hex base. Multiplying by 8 is "× 8"; a few you should know on sight:

index i012345678
i × 8 (dec)0816243240485664
i × 8 (hex)0x00x80x100x180x200x280x300x380x40

Then add to the base in hex. Example: base 0x200, element 3 → 0x200 + 0x18 = 0x218. Element 5 → 0x200 + 0x28 = 0x228. (Hex addition: add digit by digit, carry at 16. 0x8 + 0x8 = 0x10.)

%rbx points to buf[0] at address 0x3000. What address is buf[6]?

  1. 0x3006
  2. 0x3030
  3. 0x3048
  4. 0x3060

6 × 8 = 48 = 0x30. 0x3000 + 0x30 = 0x3030. (Option 3 is 6 × 12; option 4 treats the offset as decimal 60.)

You want to store %rax into buf[4], with %rbx = address of buf[0]. Which instruction does it?

  1. rmmovq %rax, 4(%rbx)
  2. mrmovq 32(%rbx), %rax
  3. rmmovq %rax, 32(%rbx)
  4. rmmovq %rax, 0x20(%rax)

buf[4] is at offset 4 × 8 = 32 = 0x20 from the base, so rmmovq %rax, 32(%rbx) (store). Option 1 uses offset 4 (wrong — that's inside buf[0]). Option 2 is a load. Option 4 uses the wrong base register.

Part C · The "stack smash" question, end to end

Here's the shape of the question you described: an array on the stack, a base pointer in %rbx, and you're asked to overwrite something beyond the array — typically the saved frame pointer or the return address. Writing past an array's end into control data is a "stack smash". The exam version is pure address arithmetic: find the offset from the base to the target, express it as an index, and write the store.

The picture

Suppose the callee allocated long buf[4] and %rbx points at buf[0]. The stack grows down, so the array sits at lower addresses and the saved %rbp and return address are above it. Concrete addresses:

AddressContentsAs an index from %rbx
0x228return address (pushed by call)buf[5]
0x220saved %rbpbuf[4]
0x218buf[3]buf[3]
0x210buf[2]buf[2]
0x208buf[1]buf[1]
0x200 ← %rbxbuf[0]buf[0]

The legal array indices are 0–3. Index 4 lands on the saved %rbp; index 5 lands on the return address. That's the slot an attacker (or an exam question) overwrites to redirect ret.

Work it out

  1. Target address → offset. Return address is at 0x228; base is 0x200. Offset = 0x228 − 0x200 = 0x28 = 40 decimal.
  2. Offset → index. 40 ÷ 8 = 5, so it's buf[5] — two slots past the end of a 4-element array.
  3. What to insert. Put the value you want to jump to (say a label/address target) in a register, then store it at that offset: 
    irmovq target, %rax       # the address to redirect ret to
rmmovq %rax, 40(%rbx)     # 40 = 0x28 = 5 × 8  → overwrites the return address
    (equivalently rmmovq %rax, 0x28(%rbx).)
  4. Where to insert it. Any time after %rbx is set to buf[0] and before the function's ret runs — because ret is what reads that slot. Put it right before the epilogue.
The three numbers the grader wants Offset from the base (target − base, in hex), the matching index (offset ÷ 8), and the store instruction (rmmovq %reg, offset(%rbx)). Get all three by subtracting hex, dividing by 8, and reading off the slot.

Same layout, but now %rbx = 0x200 points at buf[0] and you want to overwrite the saved %rbp at 0x220. What's the correct store?

  1. rmmovq %rax, 0x20(%rsp)
  2. rmmovq %rax, 4(%rbx)
  3. rmmovq %rax, 32(%rbx)
  4. mrmovq 32(%rbx), %rax

Offset = 0x220 − 0x200 = 0x20 = 32 = index 4. Store with rmmovq %rax, 32(%rbx). Option 1 uses the wrong base (%rsp), option 2 uses offset 4 (inside buf[0]), option 4 is a load.

%rbx points at buf[0] at 0x1000, and the return address sits at 0x1030. Which index of buf is the return address, and what offset do you use?

  1. buf[6], offset 48 (0x30)
  2. buf[3], offset 24 (0x18)
  3. buf[5], offset 40 (0x28)
  4. buf[48], offset 48

0x1030 − 0x1000 = 0x30 = 48. 48 ÷ 8 = 6, so buf[6], and the displacement in the instruction is 48 (or 0x30): rmmovq %rax, 48(%rbx). Watch the two conversions: subtract in hex, then divide the offset (not the raw address) by 8.

Why does overwriting that slot change where the function goes when it finishes?

  1. Because %rbp is restored from it
  2. Because %rsp is read from it
  3. Because the array bounds are stored there
  4. Because ret does popq PC — it loads the PC from that stack slot, so a new value there redirects execution

ret reads M[%rsp] (the return-address slot) into the PC. Replace the value in that slot and ret jumps wherever you wrote. That's the entire mechanism of a return-address smash.
