1 · Freeze the pipeline at cycle N

The question: five instructions, "the processor has run 6 cycles". For each instruction, say which stage it is in, or whether it has retired or has not started. You answer once for a naive pipeline and once for a pipeline that stalls but doesn't forward.

(a) Naive pipeline: pure staircase

"Naive" means the pipeline does nothing about hazards. Nothing ever waits, so instruction k is fetched in cycle k:

stage of Ik in cycle c  =  c − k      (0 = F, 1 = D, 2 = E, 3 = M, 4 = W)
                         < 0  → not started
                         > 4  → retired   (it finished W in an earlier cycle)

Cycle 6: I1 → 5 → retired, I2 → W, I3 → M, I4 → E, I5 → D. The program doesn't matter. The answer is always this diagonal.

(b) Stalling, no forwarding

The rule from slides 2.3: a consumer can't leave Decode until the producer has finished Write-back. While it waits, every instruction behind it waits too: the next one is stuck in Fetch, and anything after that hasn't started.

Producer → consumer distance1 (adjacent)234+
Stalls (no forwarding)3210

The stalled instruction shows up as F D D D D E on the slides, and the one behind it as F F F F D. Procedure: write out F/D/E/M/W cycles for each instruction in order, add stalls at each hazard, then read off the column for cycle N.

Two traps Count distance in instructions, not lines: a stall doesn't change the distance to later instructions, but it delays all of them. And "retired" means it finished W in an earlier cycle. An instruction in W during cycle 6 is still in W.

Fill in both columns, then press Check. You'll get the cycle-by-cycle working and a diagram. "New program" gives a random one.

F1. Where does addq get %rax?

irmovq $3, %rax
addq   %rax, %rbx
  1. e_valE
  2. M_valE
  3. m_valM
  4. register file

Distance 1, ALU-type producer (irmovq's value comes out of the ALU as valE). In the cycle addq is in Decode, irmovq is in Execute, so the value comes from e_valE.

F2. Where does addq get %rax?

mrmovq 0(%rdi), %rax
irmovq $1, %rcx
addq   %rax, %rbx
  1. e_valE
  2. M_valE
  3. m_valM
  4. W_valM

Distance 2, and the producer is a load, so the value is valM. When addq is in Decode the load is in Memory, reading it right now: m_valM. No stall.

F3. What happens to addq?

mrmovq 0(%rdi), %rax
addq   %rax, %rbx
  1. No stall, forwarded from e_valE
  2. 1 stall (load/use), then forwarded from m_valM
  3. 1 stall, then forwarded from W_valM
  4. 3 stalls, then the register file

The loaded value doesn't exist until the end of Memory, but addq needs it at the end of Decode, which is too early when they're adjacent. Wait one cycle: the load is now in Memory while addq is still in Decode, so it's m_valM.

F4. Where does addq get %rax?

irmovq $3, %rax
irmovq $1, %rcx
irmovq $2, %rdx
addq   %rax, %rbx
  1. e_valE
  2. M_valE
  3. W_valE
  4. register file

Distance 3, ALU value: the producer is in Write-back when addq decodes, so W_valE. (It's written to the register file at the end of that cycle, which is too late for the read.)

F5. Two writers of %rax. Where does addq get it?

irmovq $1, %rax
irmovq $2, %rax
addq   %rax, %rbx
  1. e_valE from the second irmovq
  2. M_valE from the first irmovq
  3. Both, so it's a conflict and the pipeline stalls
  4. register file

Priority goes to the nearest producer, because it holds the newest value. The forwarding logic checks e_ before M_ before W_. The answer is e_valE, giving %rax = 2.

F6. Where does mrmovq get %rsp?

pushq  %rax
mrmovq 0(%rsp), %rbx
  1. e_valE: push's new %rsp is computed by the ALU
  2. m_valM: push touches memory
  3. No hazard, because pushq doesn't write a register
  4. 1 stall (load/use)

pushq writes %rsp with valE = %rsp − 8. That's an ALU value, so it can be forwarded straight out of Execute. There's no load/use stall: push stores to memory, it doesn't load.

F7. Where does rmmovq get %rax?

mrmovq 0(%rdi), %rax
irmovq $1, %rcx
irmovq $2, %rdx
rmmovq %rax, 8(%rdi)
  1. m_valM
  2. M_valE
  3. W_valE
  4. W_valM

Distance 3 and a load, so it's valM, in the Write-back register: W_valM. (It isn't W_valE: for mrmovq valE is the address, not the data.)

3 · Throughput: SEQ vs. PIPE

From slides 2.1: each stage's logic has a delay, and every pipeline register adds a fixed overhead (20 ps on the slides).

SEQ   clock period = (sum of all stage delays) + 1 register
PIPE  clock period = (slowest stage)            + 1 register
throughput (GIPS)  = 1000 / period in ps          (one instruction finishes every period)
PIPE latency of 1 instruction = (number of stages) × PIPE period

Slide example (F 200, D 50, E 50, M 200, W 50, register 20): SEQ = 570 ps → 1.75 GIPS; PIPE = 220 ps → 4.55 GIPS. Latency goes up (570 → 1100 ps), but throughput is 2.6× higher.

Your turn. Stage delays: Fetch 150 ps, Decode 100 ps, Execute 120 ps, Memory 200 ps, Write-back 80 ps. Pipeline register: 20 ps.

T1. SEQ throughput, in GIPS (2 decimals)?

150 + 100 + 120 + 200 + 80 = 650, plus 20 = 670 ps. 1000 / 670 ≈ 1.49 GIPS.

T2. 5-stage PIPE throughput, in GIPS (2 decimals)?

Slowest stage is Memory at 200, plus 20 = 220 ps. 1000 / 220 ≈ 4.55 GIPS. Only the slowest stage matters, which is why balanced stages are the goal.

T3. Latency of a single instruction in the 5-stage PIPE, in ps?

5 stages × 220 ps = 1100 ps, more than SEQ's 670. Every instruction pays for the slowest stage five times, plus five register overheads.

T4. Throughput speedup of PIPE over SEQ (2 decimals)?

670 / 220 ≈ 3.05×. This ignores hazards. With stalls, divide by CPI, which is the real speedup.

Wording the course uses From the Lab 4 answer key: "SEQ takes one cycle per instruction" is a will always fact. "A deeper pipeline has a shorter clock period" is only is likely to, because it depends on how evenly the logic splits up.

4 · Five stages squeezed into three: |FD|EM|W|

The question merges Fetch+Decode into one stage and Execute+Memory into another, leaving Write-back alone. You're asked to compare it with the 5-stage pipeline and count stalls for a short program.

Rules I'm assuming (as I understood your description)
  • Registers are read at the end of FD and written at the end of W. Without forwarding, a consumer can't be in FD until the cycle after its producer's W (the same "wait for write-back" rule as the 5-stage pipe).
  • Forwarding: a value can go from the start of one stage to the start of another, or from anywhere in one stage to the end of another in the same cycle. That second rule is the one that matters: it's how e_valE → Decode works in the 5-stage pipe.
  • The next PC is needed at the start of FD.

Deriving the costs

No forwarding. The producer is in FD in cycle t, EM in t+1 and W in t+2, so the consumer's FD must be at t+3 or later. An adjacent consumer would naturally be in FD at t+1, so it stalls 2. At distance 2 it stalls 1, and at distance 3 or more it stalls 0. (5-stage: 3 / 2 / 1 / 0.)

With forwarding. An adjacent consumer is in FD while the producer is in EM. Both valE (ALU) and valM (memory) are produced inside EM, and the consumer only needs them by the end of FD, so "anywhere → end" covers both. That gives 0 stalls, even for load/use. In the 5-stage pipe the load/use stall exists because memory is two stages behind Decode. Here it's only one.

Control. jXX's outcome is known in EM, so only one wrong instruction (the one in FD) has been fetched: a misprediction costs 1 squash (5-stage: 2). ret's return address is read in EM, so the next fetch can happen the cycle after: 1 bubble (5-stage: 3).

Clock. The period is the slowest merged stage plus one register. With the slide numbers: FD = 200 + 50 = 250, EM = 50 + 200 = 250, W = 50, so the period is 270 ps vs. 220 ps.

5-stage3-stage |FD|EM|W|
Data stalls, adjacent, no forwarding32
Load/use with forwarding10
Mispredicted jXX2 squashed1 squashed
ret3 bubbles1 bubble
Pipeline fill+4 cycles+2 cycles
Clock period (slide numbers)220 ps270 ps

So: fewer stages means fewer and cheaper hazards, but a longer clock period. Which pipeline is faster overall depends on the program. Short, hazard-heavy code favours 3 stages; long, smooth code favours 5.

G1. Compared with the 5-stage pipeline, the 3-stage |FD|EM|W| pipeline…

  1. has a shorter clock period and fewer stalls
  2. is likely to have a longer clock period, but each hazard costs fewer (or equal) stall cycles
  3. has more stalls, because there are fewer stages to forward from
  4. will always run every program faster, because it has fewer stalls

Merging stages adds their delays together, so the slowest stage gets slower or stays the same, and so does the period. But producers and consumers are fewer stages apart, so every hazard shrinks. "Will always run faster" is wrong because the longer period can cancel out the saved stalls.

G2. 3-stage, no forwarding: how many stalls for an instruction that uses the result of the instruction right before it?

  1. 0
  2. 1
  3. 2
  4. 3

Producer: FD t, EM t+1, W t+2. Consumer needs FD ≥ t+3, but would naturally be at t+1, so it stalls 2.

G3. 3-stage, with forwarding (anywhere → end of stage): mrmovq 0(%rdi), %rax immediately followed by addq %rax, %rbx. Stalls?

  1. 0
  2. 1
  3. 2

The load reads memory during EM, in the same cycle the addq is in FD, and addq only needs the value by the end of FD. Under the "anywhere → end" rule it gets there in time. If the rule were only "start → start", it would have to wait for the value to reach the W register, which costs a stall.

irmovq $2, %rbx

G4. 5-stage, no forwarding (stalling): total data stalls?

Three distance-1 hazards (addq ← irmovq %rbx, rmmovq ← addq, addq ← mrmovq) at 3 stalls each = 9. On the first addq, %rax is at distance 2, which only needs 2 stalls, and the 3 for %rbx already cover it. Take the maximum, don't add.

G5. 3-stage, no forwarding: total data stalls?

The same three distance-1 hazards at 2 stalls each = 6.

G6. 3-stage, no forwarding: total cycles (7 instructions including halt; fill = 2)?

7 + 2 + 6 = 15. (5-stage: 7 + 4 + 9 = 20.)

G7. With the slide clock periods (5-stage 220 ps, 3-stage 270 ps) and no forwarding, which finishes this program first?

  1. 3-stage: 15 × 270 = 4050 ps vs. 20 × 220 = 4400 ps
  2. 5-stage: shorter clock period always wins
  3. They tie

This program is short and full of hazards, so the cheaper stalls and the shorter fill outweigh the slower clock.

G8. Now with forwarding: how many data stalls in the 5-stage pipeline? (The 3-stage has 0.)

Just the load/use at addq %rdx, %rax: 1. 5-stage: 7 + 4 + 1 = 12 cycles × 220 = 2640 ps. 3-stage: 7 + 2 + 0 = 9 × 270 = 2430 ps.

5 · Stalls and squashes in a loop

The procedure from Lesson 8, in short:

  1. Trace the loop by hand: how many times does it run, and which way does each jump go each time? Write that list down first.
  2. Data hazards inside the body, and across the jump back to the top: instructions squashed in between don't count toward distance.
  3. The first iteration is special. Its producers come from the setup code, not from the end of the previous iteration.
  4. Each jump: was the prediction right? Each wrong one costs 2 squashed instructions (5-stage). Every ret costs 3 bubbles.
  5. CPI = (I + 4 fill + all bubbles) / I, where I counts every executed instruction including halt (slides 2.5).

Loop A

    irmovq $3, %rcx
    irmovq $1, %r8
    irmovq $0, %rax
loop:
    addq   %rcx, %rax
    subq   %r8, %rcx
    jne    loop
    halt

The loop runs 3 times: jne is taken, taken, then not taken.

A1. How many instructions execute (including halt)?

3 setup + 3 × 3 body + halt = 13.

A2. Forwarding, predict always taken: instructions squashed?

Only the final, not-taken jne is mispredicted: 1 × 2 = 2. With forwarding there are 0 data stalls (all producers are ALU ops). CPI = (13 + 4 + 2) / 13 = 19/13 ≈ 1.46.

A3. Forwarding, predict never taken: instructions squashed?

The two taken jumps are mispredicted: 2 × 2 = 4.

A4. No forwarding (stalling), predict always taken: total data stalls?

Iteration 1: addq needs %rax from irmovq $0 at distance 1, so 3. Iterations 2 and 3: addq needs %rcx from the previous subq, with only jne in between (distance 2), so 2 each. Total 3 + 2 + 2 = 7. Plus the 2 squashed from A2.

Loop B: a load inside the body

    irmovq array, %rdi
    irmovq $4, %rcx
    irmovq $8, %r9
    irmovq $1, %r8
    xorq   %rax, %rax
loop:
    mrmovq 0(%rdi), %rdx
    addq   %rdx, %rax       # sum += *p
    addq   %r9, %rdi        # p++
    subq   %r8, %rcx
    jne    loop
    halt
array: .quad 1, 2, 3, 4     # (one .quad per line in real y86)

B1. Forwarding, predict always taken: total data stalls?

A load/use stall on addq %rdx, %rax every iteration: 4 × 1 = 4. Everything else forwards. (The fix: move addq %r9, %rdi between the load and its use, which gets you 0. That's Lesson 3's scheduling trick.)

B2. Same setup: instructions squashed?

Four iterations, so jne is taken 3 times and not taken once. Always-taken misses once: 2. (Never-taken would miss 3 times: 6.)

B3. CPI (2 decimals)?

I = 5 + 4 × 5 + 1 = 26. CPI = (26 + 4 + 4 + 2) / 26 = 36/26 ≈ 1.38.
