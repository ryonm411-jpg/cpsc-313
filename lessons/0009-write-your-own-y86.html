Write Your Own Y86

Six problems where you write the code. Type it, hit Run, and it's checked against several inputs — then you see exactly how your program behaves in the pipeline. This is the "write a program and predict its pipeline behaviour" goal, practised for real.

How this works Each problem has an editor pre-loaded with a skeleton. Write your solution, press Run & check, and it runs your code through the Y86 interpreter on several test inputs. Green = all cases pass. On success you get the pipeline read-out (instructions, bubbles, CPI). Show solution reveals one correct version — only after you've tried.

A method for writing Y86 (use it on every problem)

You struggle to start from a blank editor. Don't start blank — start from this skeleton and fill the blanks. Almost every Quiz 2 coding problem is "initialise, loop over something, combine, finish":

# 1. Put each C variable in a register. Arguments arrive in %rdi, %rsi, %rdx, …; result leaves in %rax.
# 2. Materialise every constant you need (irmovq) — you can't use $imm in addq/subq.
# 3. Guard the loop so the body can be skipped (handles the n = 0 case).
# 4. Body: do the work, advance the pointer/counter.
# 5. Test and branch back. Remember subq is destructive and there is no cmpq.

    irmovq $0, %rax        # result accumulator
    irmovq $8, %r8         # stride (8 bytes per long), if walking an array
    irmovq $1, %r9         # the constant 1, for counting
    andq %rsi, %rsi        # test the count WITHOUT destroying it (n & n = n)
    jle done               # body runs zero times if n <= 0
loop:
    # ... the work ...
    addq %r8, %rdi         # a++  (advance pointer by 8)
    subq %r9, %rsi         # n--  (and this sets the flags on the new n)
    jg loop                # repeat while n > 0
done:
    halt
The four rules that bite in the pipeline too
  1. No $imm in arithmetic. addq $1, %rsi is illegal — load 1 into a register first.
  2. subq %rA, %rB writes %rB. To compare without losing a value, use andq %rX, %rX (test against 0) or subtract into a scratch copy.
  3. Only OPq sets condition codes. A jle reads the flags from the most recent addq/subq/andq, not from a mrmovq or rrmovq.
  4. Loads feed uses one cycle late. An mrmovq immediately followed by an instruction that uses its result costs a load/use bubble — the pipeline read-out will show it. You'll exploit this in Problem 6.

Problem 6 · schedule away the stalls — same result, fewer bubbles

This one is pure Quiz 2: the starter code is correct but stalls — each addq waits for the mrmovq right above it (a load/use hazard). Reorder the instructions so your result is unchanged but the pipeline read-out shows 0 data-stall bubbles. The checker confirms correctness; you read the bubble count.

Where these show up on the quiz Problems 1 and 6 are the heart of "write a program with a conditional jump / schedule it and predict the pipeline behaviour." Count the bubbles each one reports and practise saying why (control hazard on the jump; load/use hazards before you reorder). Then try changing the predictor in your head: would always-taken vs BTFNT change the squash count?
